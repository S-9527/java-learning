这一课讲 JDK 5 之后给的更灵活的锁——`ReentrantLock`。

## 一、先让代码疼一次：`synchronized` 只会傻等

假设一个场景：两个线程要改同一份数据，但**其中一个只在"有空"时才愿意等**。

用 `synchronized` 写出来是这样的：

```java
public synchronized void update() {
    // 拿不到锁就在这里一直等，没有超时，没有退路
}
```

问题在于：

- 它**不能超时**——对方卡死了，你也跟着卡死
- 它**不能中断**——你没法用 `interrupt()` 把它叫回来
- 它**不能尝试**——拿不到就只能等，没法"先去看看别的活"
- 它**只有一个等待队列**——`wait` / `notifyAll` 会把所有等待者一起叫醒，
  哪怕只有一部分人真正等到了想要的条件

`ReentrantLock` 把这几件事都变成了可控的。

---

## 二、正解：`ReentrantLock` 的基本用法

```java
private final Lock lock = new ReentrantLock();

public void increment() {
    lock.lock();                    // 手动上锁
    try {
        count++;
    } finally {
        lock.unlock();              // 必须在 finally 里释放
    }
}
```

```terminal
========== 1. Lock 的基本用法：unlock 必须放 finally ==========
  拿到锁，count = 1
  释放后 isLocked = false
```

### 2.1 为什么 `unlock` 必须在 `finally` 里

这是 `Lock` 和 `synchronized` 最关键的差别：

| | 出异常时锁怎么办 |
|---|---|
| `synchronized` | JVM 自动帮你释放 |
| `ReentrantLock` | **必须自己释放，不释放就永远不还** |

想一下如果中间抛了异常而你没释放锁，会发生什么？——
这个锁**永远不会被还回来**，其他所有线程全部卡死。这就是**死锁**。

宁可多写三行 `try/finally`，也不要赌"这里不会抛异常"。

### 2.2 和 `synchronized` 怎么选

| | `synchronized` | `ReentrantLock` |
|---|---|---|
| 写法 | 简单 | 要手写 lock/unlock |
| 释放 | 自动 | 必须 finally |
| 超时 | 不支持 | `tryLock(timeout)` |
| 可中断 | 不支持 | `lockInterruptibly()` |
| 公平锁 | 不支持 | 支持 |
| 多个等待队列 | 不支持 | `Condition` |
| 性能 | JVM 优化得好 | 差不多，高竞争下略优 |

**结论：初学阶段用 `synchronized` 就够了。** 需要上面那几样能力时再换 `Lock`。

## 三、`tryLock`：拿不到就走

这是 `synchronized` 做不到的第一件事。

```java
boolean got = lock.tryLock();      // 拿得到返回 true，拿不到立刻返回 false
if (got) {
    try { /* 干活 */ } finally { lock.unlock(); }
} else {
    /* 干点别的，或者直接返回 */
}
```

```terminal
========== 2. tryLock：拿不到就走，不干等 ==========
  另一个线程持有锁时，tryLock() → false
  耗时 0 毫秒 ← 立刻返回，没干等（不到 1 毫秒）
  对方释放后再 tryLock() → true
```

"耗时 0 毫秒"就是重点——它**没有阻塞**。

### 3.1 带超时的版本

```java
boolean got = lock.tryLock(300, TimeUnit.MILLISECONDS);
```

```terminal
========== 3. tryLock 超时：等一会儿就走 ==========
  tryLock(300ms) → false
  等了 至少 300 毫秒才放弃 ← 它真的等满了超时时间
```

它等满 300 毫秒，还是拿不到，就放弃。这个能力在实战里很有用——
比如"拿不到锁就降级走另一条路"，而不是把线程一直挂在那儿。

### 3.2 一个我踩过的坑

写这一课的测试时，我写了一条断言：

```java
lock.lock();
assertThat(lock.tryLock()).isFalse();   // ← 这条是错的
```

**它失败了。** 因为 `lock.tryLock()` 在**同一线程**里会返回 `true`——
锁是**可重入**的，同一个线程再拿一次不会失败。

"拿不到"只发生在**别的线程**身上。所以演示 `tryLock` 失败时，
必须让**另一个线程**持有锁（本课的 demo 就是用 `CountDownLatch`
让一个 holder 线程先拿到锁，主线程再试）。

这个坑本身就是下一节要讲的"可重入"。

## 四、可重入：同一线程能重复拿

```java
lock.lock();
System.out.println(lock.getHoldCount());   // 1
lock.lock();
System.out.println(lock.getHoldCount());   // 2
```

```terminal
========== 4. 可重入：同一线程能重复拿同一把锁 ==========
  第一次 lock 之后 holdCount = 1
  第二次 lock 之后 holdCount = 2
  释放一次之后 holdCount = 1
  全部释放之后 isLocked = false
```

**可重入**（reentrant）的意思是：同一个线程已经持有某把锁，
它再次申请这把锁**可以直接拿到**，不会自己把自己锁死。

`ReentrantLock` 内部维护一个计数器（`getHoldCount()`）：
每 `lock()` 一次加一，每 `unlock()` 一次减一，**减到 0 才真正释放**。

所以有一条容易犯的错：**lock 了几次就要 unlock 几次**。
只 unlock 一次，锁还在你手里。

`synchronized` 也是可重入的——第 13 课演示过"`a()` 里调 `b()`"那个例子。

## 五、公平锁 vs 非公平锁

```java
new ReentrantLock()        // 非公平（默认）
new ReentrantLock(true)    // 公平
```

```terminal
========== 5. 公平锁 vs 非公平锁 ==========
  new ReentrantLock()      isFair = false
  new ReentrantLock(true)  isFair = true
  ← 默认是非公平的，吞吐更高但可能饿死某个线程
```

| | 公平锁 | 非公平锁（默认） |
|---|---|---|
| 拿锁顺序 | 严格按排队顺序 | 允许插队 |
| 吞吐量 | 较低（要维护队列） | **较高** |
| 风险 | 无 | 极端情况下某线程可能一直抢不到（饿死） |

**为什么默认不公平？** 因为"刚释放锁的线程马上又拿到锁"这种情况很常见，
让它可以插队能减少线程切换，整体吞吐更高。公平锁适合"不允许有人等太久"的场景。

## 六、`Condition`：一个锁配多个等待队列

这是 `ReentrantLock` 相对 `synchronized` 最有价值的一个能力。

`wait` / `notifyAll` 只有一个等待队列，`notifyAll` 会把**所有**等待者都叫醒——
哪怕只有一部分人真正等到了想要的条件。`Condition` 把等待者分组：

```java
ReentrantLock lock = new ReentrantLock();
Condition notFull  = lock.newCondition();    // 等"不满"的队列
Condition notEmpty = lock.newCondition();    // 等"不空"的队列

// 消费者：仓库空了就去 notEmpty 上等
notEmpty.await();

// 生产者：放了一个元素，只叫醒等 notEmpty 的
notEmpty.signal();      // notFull 那个队列完全不受影响
```

```terminal
========== 6. Condition：一个锁配多个等待队列 ==========
  消费者：仓库空了，去 notEmpty 队列上等
  生产者：放了一个元素，只唤醒 notEmpty 队列
  消费者：被叫醒了
  ← 两个队列互不干扰，这就是 Condition 比 wait/notify 强的地方
```

经典应用是**有界阻塞队列**（生产者-消费者模型）：
生产者只在"队列没满"时等，消费者只在"队列没空"时等，
两边用各自的 `Condition`，互不打扰。

`Condition` 的 `await` / `signal` 必须**先持有对应的锁**，否则抛
`IllegalMonitorStateException`——和 `wait` / `notify` 的规矩一样。

## 七、死锁：两个线程互相等对方的锁

```java
// 线程 1
synchronized (lockA) {
    sleep(100);
    synchronized (lockB) { ... }    // 等 B
}

// 线程 2
synchronized (lockB) {
    sleep(100);
    synchronized (lockA) { ... }    // 等 A
}
```

```terminal
========== 7. 死锁：两个线程互相等对方的锁 ==========
  1 秒后 t1 还活着吗 → true
  1 秒后 t2 还活着吗 → true
  两个线程的状态：t1=BLOCKED，t2=BLOCKED
  ← 两个都卡住了：t1 拿着 A 等 B，t2 拿着 B 等 A
  ← 死锁四条件：互斥、持有并等待、不可剥夺、循环等待
  ThreadMXBean 找到的死锁线程数 → 2
```

### 7.1 死锁的四个必要条件

四条**同时**成立才会死锁，破坏任意一条就能避免：

| 条件 | 含义 | 怎么破坏 |
|---|---|---|
| **互斥** | 资源同一时刻只能一个线程用 | 难破坏（锁的本质） |
| **持有并等待** | 拿着一个还去要另一个 | **一次性申请所有锁** |
| **不可剥夺** | 别人不能抢走你手里的锁 | 用 `tryLock` 抢不到就放弃 |
| **循环等待** | A 等 B，B 等 A | **给锁定个全局顺序，大家都按顺序拿** |

最实用的两条：**统一加锁顺序**（比如永远先拿 `lockA` 再拿 `lockB`），
以及**用 `tryLock` 拿不到就退回去重试**。

### 7.2 怎么发现死锁

上面最后一行是重点——**JVM 自己知道**：

```java
ThreadMXBean mx = ManagementFactory.getThreadMXBean();
long[] deadlocked = mx.findDeadlockedThreads();   // 返回死锁的线程 id
```

线上排查死锁用的 `jstack` 内部就是查这个。`jstack <pid>` 会直接告诉你
"Found one Java-level deadlock"，并列出每个线程在等哪把锁。

### 7.3 演示死锁的一个技术细节

死锁的两个线程是**永远不会结束**的。如果不管它们，JVM 就不会退出
（因为它们是用户线程）。演示时必须**在 `start()` 之前**设成守护线程：

```java
t1.setDaemon(true);      // ← 必须在 start() 之前
t1.start();
```

写这一课时我把 `setDaemon(true)` 写在了 `start()` 后面，直接抛：

```
java.lang.IllegalThreadStateException
    at java.base/java.lang.Thread.setDaemon(Thread.java:2044)
```

**`setDaemon` 只能在 `start()` 之前调用**，启动之后再设就晚了。
这个错误我留在了测试里（`setDaemonMustComeBeforeStart`），
因为它是很容易踩的一个坑。

## 八、不推荐的用法

- **别忘记在 `finally` 里 `unlock`**。这是 `Lock` 最容易出事的地方，
  出一次就是全线卡死
- **别 `lock()` 两次只 `unlock()` 一次**。可重入意味着计数，
  少还一次锁就一直在你手里
- **别在持有锁的时候做耗时操作**（IO、网络、`sleep`）。
  锁的持有时间越短越好——你拿着锁睡觉，别人全都得等着
- **别用多个锁还不管顺序**。加锁顺序不统一是死锁最常见的成因
- **别以为用了 `Lock` 就比 `synchronized` 高级**。绝大多数场景
  `synchronized` 更省心、更不容易写错

## 九、这一课的术语表

- **`Lock`** —— JDK 5 引入的锁接口，比 `synchronized` 更灵活
- **`ReentrantLock`** —— 可重入的 `Lock` 实现，最常用
- **可重入**（reentrant）—— 同一线程能重复获取已持有的锁，计数管理
- **`tryLock`** —— 尝试获取锁，拿不到不阻塞；支持超时
- **`lockInterruptibly`** —— 可被 `interrupt()` 打断的加锁，区别于傻等
- **公平锁**（fair lock）—— 严格按排队顺序发锁；默认是非公平
- **`Condition`** —— 锁上的条件变量，一个锁可配多个等待队列
- **`await` / `signal`** —— `Condition` 上的等待与唤醒，必须持有对应锁
- **死锁**（deadlock）—— 互相等对方持有的资源，全部永久阻塞
- **死锁四条件** —— 互斥、持有并等待、不可剥夺、循环等待
- **`ThreadMXBean`** —— 可以查询死锁线程的 JMX 接口，`jstack` 的基础
- **守护线程**（daemon thread）—— 用户线程全结束后 JVM 就退出，不管它跑没跑完
