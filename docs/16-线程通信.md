上一课讲的锁解决的是**互斥**——同一时刻只让一个人干。

但多线程不只是互斥，还有**协作**：一个线程得等另一个线程准备好才能继续。
比如生产者往队列里放东西，消费者得等"有东西了"才能取；
队列满了，生产者得等"有人取走了"才能继续放。

`synchronized` 只管"不许同时进"，管不了"等某个条件成立再进"。
这就需要 `wait` / `notify`。

先看全貌：

```terminal
$ java src/main/java/dev/javalearning/concurrency/coordination/CoordinationDemo.java

========== 1. wait/notify 必须在 synchronized 里，否则直接抛异常 ==========
  不在 synchronized 里调 wait   → IllegalMonitorStateException
  不在 synchronized 里调 notify → IllegalMonitorStateException
  ← 因为 wait/notify 操作的是「对象上的监视器」，必须先持有它

========== 2. wait 会释放锁，sleep 不会——这是最容易混的一点 ==========
  wait 期间，别的线程能拿到同一把锁吗 → true
  sleep 期间，别的线程能拿到同一把锁吗 → false

========== 3. 用 wait/notify 写一个生产者-消费者队列 ==========
  [1] 生产者放入 1
  [2] 生产者放入 2

  [4] 消费者取到 1

  容量 1 的队列，放满之后生产者还在跑吗 → true
```

## 一、先让代码疼一次

假设要写一个队列，生产者放、消费者取。用 `synchronized` 只能保证不冲突：

```java
synchronized void put(T item) { items.add(item); }

synchronized T take() {
    if (items.isEmpty()) {
        return null;      // ← 只能返回 null，让调用方自己重试
    }
    return items.poll();
}
```

调用方就变成了**忙等**（busy waiting）：

```java
while ((item = queue.take()) == null) {
    // 空转，CPU 全浪费在"再试一次"上
}
```

这样有两个问题：**浪费 CPU**，而且**响应不及时**——取到之后还要等下一次循环。

我们需要的是：**队列空的时候，消费者就挂起，等有东西了再被叫醒。**

这就是 `wait` / `notify` 要干的事。

---

## 二、`wait` / `notify` 的三条铁律

### 2.1 必须在 `synchronized` 里调用

```terminal
========== 1. wait/notify 必须在 synchronized 里，否则直接抛异常 ==========
  不在 synchronized 里调 wait   → IllegalMonitorStateException
  不在 synchronized 里调 notify → IllegalMonitorStateException
  ← 因为 wait/notify 操作的是「对象上的监视器」，必须先持有它
```

原因：`wait` / `notify` 操作的不是"线程"，而是**某个对象上的监视器**（monitor）。
你得先持有它，才有资格操作它的等待队列。

所以 `wait` / `notify` 永远长这样：

```java
synchronized (lock) {
    lock.wait();
}
```

### 2.2 `wait` 会释放锁，`sleep` 不会

这是最容易搞混的一点，我们用真实实验证明：

```terminal
========== 2. wait 会释放锁，sleep 不会——这是最容易混的一点 ==========
  wait 期间，别的线程能拿到同一把锁吗 → true
  sleep 期间，别的线程能拿到同一把锁吗 → false
```

实验做法：一个线程在同步块里 `wait`（或 `sleep`），主线程随后尝试进入
**同一个同步块**。

| | 调用期间锁的状态 | 别的线程能进吗 |
|---|---|---|
| `wait()` | **释放** | 能 |
| `Thread.sleep()` | **仍持有** | 不能 |

**这个区别至关重要**：如果 `wait` 不释放锁，那么消费者在等"有东西"的时候
还把锁攥着，生产者根本进不来放东西——**永远死锁**。

`wait` 释放锁，正是为了让别人能进来改变条件。

### 2.3 被唤醒后要重新抢锁

`wait` 返回并不意味着你立刻继续执行。醒来后你要**重新竞争这把锁**，
抢到了才从 `wait` 那行往下走。这个细节在写循环时很重要。

## 三、标准写法：`while` + `wait`

这是所有 `wait` 的标准姿势：

```java
synchronized void put(T item) {
    while (items.size() >= capacity) {    // ← 用 while，不是 if
        wait();                            // 满了就等
    }
    items.add(item);
    notifyAll();                           // 通知等"非空"的消费者
}

synchronized T take() {
    while (items.isEmpty()) {              // ← 同样用 while
        wait();                             // 空了就等
    }
    T item = items.poll();
    notifyAll();                            // 通知等"不满"的生产者
    return item;
}
```

完整实现就在 [`CoordinationDemo.java`](../src/main/java/dev/javalearning/concurrency/coordination/CoordinationDemo.java)
里的 `SimpleQueue`。跑起来是这样：

```terminal
========== 3. 用 wait/notify 写一个生产者-消费者队列 ==========
  [1] 生产者放入 1
  [2] 生产者放入 2
  [3] 生产者放入 3
  [4] 消费者取到 1
  [5] 消费者取到 2
  [6] 消费者取到 3
  ← 两边用同一个监视器互相通知，谁都不忙等
  ← 真实的事件交错顺序每次可能不同，这里按编号排好再打印
  容量 1 的队列，放满之后生产者还在跑吗 → true
  消费者取走 1 之后，生产者放完了吗 → false
  ← put 在队列满时用 wait 挂起，被 take 的 notifyAll 叫醒
```

后面两行是重点：**容量 1 的队列，生产者放满之后真的挂起了**
（`还在跑吗 → true`），一直等到消费者取走才继续。

> 顺带说明：这个 demo 的日志是按事件编号排好序再打印的。
> 真实的事件交错顺序每次运行都可能不同——这一点我在代码注释里也标了。

### 3.1 为什么必须用 `while` 而不是 `if`

因为 `wait` 可能在**没有通知**的情况下自己醒来，这叫**虚假唤醒**
（spurious wakeup）。也可能醒来时条件又被别人抢走了。

用 `if` 只检查一次，条件不成立就会直接往下跑：

```java
if (items.isEmpty()) {
    wait();
}
// 醒来后不检查，直接 poll —— 队列可能还是空的
items.poll();
```

用 `while` 的话，醒来后会**重新检查**，不成立就接着睡。看真实输出：

```terminal
========== 4. 为什么用 while 而不是 if 包住 wait ==========
  waiter：条件不成立，继续等
  main：先 notify 一次，但条件还是 false
  waiter：条件不成立，继续等
  main：这次把条件设为 true 再 notify
  waiter：条件成立，继续干活
```

我故意先 `notify` 一次但**不改变条件**——模拟虚假唤醒。
`while` 版本正确地又睡回去了。

**记住这句话**：`wait` 永远写在 `while` 里，永远不用 `if`。

## 四、`notify` vs `notifyAll`

| | 行为 |
|---|---|
| `notify()` | 随机叫醒**一个**等待者 |
| `notifyAll()` | 叫醒**全部**等待者 |

```terminal
========== 5. notify 只叫醒一个，notifyAll 叫醒全部 ==========
  调 notify()，只叫醒一个
  等待者 1 被叫醒
  调 notifyAll()，把剩下的都叫醒
  等待者 2 被叫醒
  等待者 3 被叫醒
  ← notify 叫醒哪个是不确定的，所以多个等待者时一般用 notifyAll
```

**`notify` 叫醒哪个是不确定的**（由 JVM 实现决定）。如果被叫醒的那个
恰好不满足条件（比如你叫醒了等"非空"的人，但队列其实还是空的），
它就会睡回去——而真正该醒的那个还在睡，**可能永远等下去**。

所以结论很简单：

> **不确定的时候一律用 `notifyAll()`。** 被多叫醒的人醒来发现条件不满足，
> 会自己睡回去（前提是你用了 `while`），代价只是一点点性能。

这也是为什么第 15 课讲的 `Condition` 有价值——它能**精确叫醒某一组**等待者，
既不用叫醒所有人，也不会叫错人。

## 五、`wait` / `notify` vs `Condition`

| | `wait` / `notify` | `Condition` |
|---|---|---|
| 从哪来 | `Object` 的方法 | `Lock.newCondition()` |
| 等待队列 | **只有一个** | 一个锁可配**多个** |
| 唤醒精度 | 只能随机叫一个或全叫 | 精确叫醒指定的那组 |
| 必须持有 | `synchronized` 的监视器 | 对应的 `Lock` |

`Condition` 的 `await` / `signal` 是 `wait` / `notify` 的对应物，
用法完全一样（也要用 `while` 包住），只是分成了多个队列。

## 六、`InterruptedException` 怎么处理

`wait` 会抛 `InterruptedException`，因为它是可中断的（这是好事——
你不想让它永远卡着）。标准处理是**恢复中断标志**：

```java
try {
    lock.wait();
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();   // ← 把标志设回去
    return;                                // 该退出了
}
```

为什么不能"吞掉"异常什么都不做？因为**中断标志被清除了**，
上层代码再也没法知道"有人要求我停下"。

这条规矩对 `sleep`、`join`、`await` 全都适用。

---

## 七、不推荐的用法

- **别在 `synchronized` 外面调 `wait` / `notify`**。直接抛
  `IllegalMonitorStateException`
- **别用 `if` 包 `wait`**。必须 `while`，否则虚假唤醒会让你的程序冲出去
- **别用 `notify` 而不确定等待者是谁**。默认用 `notifyAll`
- **别在持有锁的时候做耗时操作**。`wait` 会释放锁，但 `wait` 前后那段
  代码还在锁里
- **别自己手写阻塞队列了**（学习除外）。JDK 有 `ArrayBlockingQueue`、
  `LinkedBlockingQueue`，它们把这些细节都处理好了，而且性能更好。
  下一课就会讲线程池怎么用它们
- **别吞掉 `InterruptedException`**

## 八、这一课的术语表

- **线程通信**（thread coordination）—— 线程之间互相等待、通知的机制
- **`wait()`** —— 释放锁并进入等待，直到被通知 / 中断 / 超时
- **`notify()` / `notifyAll()`** —— 唤醒一个 / 全部等待者，必须先持有监视器
- **监视器**（monitor）—— 每个对象都有的内置锁；`wait` / `notify` 操作的对象
- **虚假唤醒**（spurious wakeup）—— `wait` 在没有通知的情况下自己醒来，
  所以必须用 `while` 重新检查条件
- **`IllegalMonitorStateException`** —— 没持有监视器就调 `wait` / `notify`
- **忙等**（busy waiting）—— 循环里反复重试，浪费 CPU；`wait` 就是为了避免它
- **生产者-消费者**（producer-consumer）—— 最经典的线程通信模型
- **`InterruptedException`** —— 等待时被 `interrupt()` 打断；处理方式是恢复中断标志
- **`Condition`** —— `Lock` 上的条件变量，可以配多个等待队列
