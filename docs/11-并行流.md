# 11 · 并行流

> 状态：✅ 讲完了　·　最后更新：2026-10-12

[Stream API](./10-Stream.md)那一课我们把流用熟了。但有个问题一直没说：
**`stream()` 是单线程的**。数据量大的时候，多核机器上其他核都闲着。

并行流就是"用上多核"的最短路径——**加一个方法调用**。但这一课要讲的是：
那个方法调用为什么不能随便加。

先看全貌：

```terminal
$ java src/main/java/dev/javalearning/stream/ParallelStreamDemo.java

========== 1. 怎么创建并行流 ==========
  letters.stream().parallel() 的元素数 → 6
  letters.parallelStream()     的元素数 → 6
  ← 一个是在顺序流上转，一个是集合直接给

========== 2. 第一次撞墙：forEach 的输出是乱序的 ==========
  原始顺序          → [a, l, b, e, r, t]
  forEach 收到的集合（排序后打印）→ [a, b, e, l, r, t]
  ← 元素一个不少，但**到达顺序**和原始顺序无关
  ← 谁先跑完谁先 add，所以这里必须排序后再打印，否则输出会随机变化
  ← 想看乱序的原始样子：多跑几次这个 demo，输出顺序会变

========== 3. forEachOrdered：保序，但牺牲并行效率 ==========
  forEachOrdered 收到的顺序 → [a, l, b, e, r, t]
  和原始顺序一致吗 → true
  ← 它按「出现顺序」执行，代价是部分并行度被牺牲

========== 4. 为什么 collect(toList) 的结果却是有序的 ==========
  collect(toList()) 的结果 → [a, l, b, e, r, t]
  ← 明明是多线程跑的，为什么还有序？下一节拆开看
  收集到 TreeSet（排过序）→ [a, b, e, l, r, t]
  ← 注意：无序是 Set 这个容器导致的，不是并行导致的

========== 5. 自定义 Collector：看合并过程到底发生了什么 ==========
  结果 → [a, l, b, e, r, t]
  supplier 被调用了不止一次吗 → true
  combiner 被调用过吗 → true
  ← 每个分片各有一个局部容器，最后按顺序合并起来
  ← 分几片取决于 CPU 核数，所以这里不打印具体次数
  换成顺序流：supplier 1 次，combiner 0 次
  ← 顺序流只用一个容器，压根不需要合并

========== 6. 哪些操作并行后结果不变 ==========
  count  顺序 100 / 并行 100  一致吗 → true
  sum    顺序 5050 / 并行 5050  一致吗 → true
  max    顺序 100 / 并行 100  一致吗 → true
  ← 这些操作与元素顺序无关：先分片各算各的，再合并结果

========== 7. reduce 用非结合性操作会出错（经典坑） ==========
  加法（结合性）  顺序 10 / 并行 10  一致吗 → true
  减法（非结合性）顺序 -10 / 并行 0  一致吗 → false
  ← 减法不满足 (a-b)-c = a-(b-c)，并行分段算完再合并就错了
  ← 并行流的结果甚至可能每次不同，取决于分片方式
  乘法（结合性）  顺序 24 / 并行 24  一致吗 → true

========== 8. 并行流里操作共享集合会出问题 ==========
  用 ArrayList 收集 10 万个，出问题了吗 → true
  （可能是丢元素，也可能直接抛异常，每次运行都可能不同）
  换成 collect 收集 → 收到 100000 个
  ← collect 给每个分片一个局部容器，最后合并，所以是安全的
  ← 而 forEach 直接往共享集合里塞，多个线程同时 add 就出事

========== 9. 用的是哪个线程池 ==========
  ForkJoinPool.commonPool 的并行度 → 15
  Runtime 报告的 CPU 核数 → 16
  ← 并行度通常等于核数减一（留一个给主线程）
  ← 关键：整个 JVM 共享这一个池，一个并行流卡住会影响别的并行流

========== 10. 并行流一定更快吗 ==========
  100 个元素：顺序 5050 / 并行 5050  结果一样吗 → true
  ← 数据量小的时候，并行的线程调度开销可能比省下的时间还多
  ← 这里故意不打印耗时：微基准抖动太大，贴出来会误导
  ← 结论：数据量大 + 计算密集 + 无状态，才考虑并行
```

> **关于这一课的输出**：并行流的输出天生不稳定，这是它的本质。
> 所以我在 demo 里做了处理：**凡是顺序不确定的地方，都排序后再打印**，
> 只把"是否乱序"作为结论告诉你。想看乱序的原始样子，多跑几次 demo。

## 一、先让代码疼一次

[Stream API](./10-Stream.md)里我们写过这样的代码：

```java
List<String> result = people.stream()
        .filter(p -> p.age() > 18)
        .map(Person::name)
        .collect(Collectors.toList());
```

这段代码只用一个线程。如果 `people` 有一千万条，而机器有 16 个核，
那 15 个核在围观。

**改成并行只要加一个词**：

```java
people.parallelStream()          // 或者 people.stream().parallel()
```

听起来太美了。跑一下第 2 节：

```terminal
========== 2. 第一次撞墙：forEach 的输出是乱序的 ==========

  forEach 收到的集合（排序后打印）→ [a, b, e, l, r, t]
  ← 元素一个不少，但**到达顺序**和原始顺序无关
```

**元素一个不少，但顺序没了。**

## 二、正解：并行流的三条规矩

### 2.1 规矩一：`forEach` 不保证顺序，`forEachOrdered` 保

```terminal
========== 3. forEachOrdered：保序，但牺牲并行效率 ==========
  forEachOrdered 收到的顺序 → [a, l, b, e, r, t]
  和原始顺序一致吗 → true
```

| | 顺序 | 效率 |
|---|---|---|
| `forEach` | **不保证** | 高 |
| `forEachOrdered` | 保证（按出现顺序） | 低一些 |

**为什么 `forEachOrdered` 会慢**？因为某个分片即使先算完了，
如果它在"逻辑上"排在后面，也得等前面的分片处理完才能执行动作。
并行度被这个"排队"约束吃掉一部分。

### 2.2 规矩二：`collect` 的结果是保序的（这需要解释）

这里有个矛盾：明明是多线程跑的，为什么 `collect(toList())` 有序？

```terminal
========== 4. 为什么 collect(toList) 的结果却是有序的 ==========
  collect(toList()) 的结果 → [a, l, b, e, r, t]
```

答案在第 5 节——把 `Collector` 拆开看：

```terminal
========== 5. 自定义 Collector：看合并过程到底发生了什么 ==========
  supplier 被调用了不止一次吗 → true
  combiner 被调用过吗 → true
  ← 每个分片各有一个局部容器，最后按顺序合并起来
  换成顺序流：supplier 1 次，combiner 0 次
```

`Collector` 的四个组件（[Stream API](./10-Stream.md)提过）在这里全用上了：

```
并行流处理一个集合时：

  数据源  [a, l, b, e, r, t]
            ↓ 分片（Spliterator）
  ┌────────┬────────┬────────┐
  │ 分片1   │ 分片2   │ 分片3   │
  │ supplier│ supplier│ supplier│   ← 每个分片各建一个局部容器
  │ accumul │ accumul │ accumul │   ← 各自往里塞
  └────┬───┴────┬───┴────┬───┘
       └────────┼────────┘
            combiner                ← 按区段顺序合并
                ↓
          [a, l, b, e, r, t]        ← 合并时保序
```

**关键点**：分片时 `Spliterator` **保留了区段顺序信息**，
合并时 ForkJoin 框架按这个顺序合并。所以即使分片 3 先算完，
它也会等分片 1、2 合并完再合并——结果就有序了。

**而 `forEach` 没有合并这一步**，谁先算完谁就执行动作，所以无序。

这也解释了第 4 节最后一行：

```terminal
  收集到 TreeSet（排过序）→ [a, b, e, l, r, t]
  ← 注意：无序是 Set 这个容器导致的，不是并行导致的
```

`Set` 本身无序，跟并行没关系。

### 2.3 规矩三：结果一致的操作 vs 可能出错的操作

这是最实用的一张表：

| 操作 | 并行后结果 | 为什么 |
|---|---|---|
| `count` / `sum` / `max` / `min` / `average` | **一致** | 与顺序无关，先分片算再合并 |
| `anyMatch` / `allMatch` / `noneMatch` | **一致** | 短路操作 |
| `findFirst` | **一致** | 保序查找 |
| `distinct` / `sorted` | **一致** | 有状态操作，分片处理后再次合并 |
| `collect` | **一致**（保序容器） | 见 2.2 |
| `forEach` | **不保证顺序** | 没有合并步骤 |
| `reduce`（**非结合性**操作） | **可能不一致** | 见下一节 |

```terminal
========== 6. 哪些操作并行后结果不变 ==========
  count  顺序 100 / 并行 100  一致吗 → true
  sum    顺序 5050 / 并行 5050  一致吗 → true
  max    顺序 100 / 并行 100  一致吗 → true
```

## 三、最经典的坑：`reduce` 的非结合性

```terminal
========== 7. reduce 用非结合性操作会出错（经典坑） ==========
  加法（结合性）  顺序 10 / 并行 10  一致吗 → true
  减法（非结合性）顺序 -10 / 并行 0  一致吗 → false
  乘法（结合性）  顺序 24 / 并行 24  一致吗 → true
```

**同一份数据、同一个操作，顺序流得 `-10`，并行流得 `0`。**

### 为什么

`reduce` 要求你给的操作满足**结合律**（associativity）：

```
(a op b) op c  ==  a op (b op c)
```

- 加法：`(1+2)+3 == 1+(2+3)` ✅ 满足
- 乘法：满足 ✅
- **减法：`(1-2)-3 = -4`，但 `1-(2-3) = 2`** ❌ 不满足

顺序流是严格从左往右算的：

```
((0 - 1) - 2) - 3) - 4 = -10
```

并行流把数据**分段**，各段独立算，再合并：

```
分片1: 0 - 1 = -1
分片2: 0 - 2 = -2        ← 每段都从初始值 0 开始
分片3: 0 - 3 = -3
分片4: 0 - 4 = -4
合并:  ((-1 - -2) - -3) - -4 = 0
```

（具体的分片方式取决于核数，所以**并行的结果本身也不稳定**——
第 7 节那个 `0` 只是我这次运行的结果。）

### 结论

> **用 `reduce` 之前先问自己：这个操作满足结合律吗？**
> 不满足就别用并行流（顺序流是安全的）。

## 四、并行流里别碰共享可变状态

```terminal
========== 8. 并行流里操作共享集合会出问题 ==========
  用 ArrayList 收集 10 万个，出问题了吗 → true
  （可能是丢元素，也可能直接抛异常，每次运行都可能不同）
  换成 collect 收集 → 收到 100000 个
```

```java
// ❌ 错：多个线程同时往一个 ArrayList 里 add
List<Integer> unsafe = new ArrayList<>();
IntStream.range(0, 100_000).parallel().forEach(unsafe::add);
// 结果：可能少元素，也可能直接抛 ArrayIndexOutOfBoundsException

// ✅ 对：collect 给每个分片一个局部容器，最后合并
List<Integer> safe = IntStream.range(0, 100_000).parallel()
        .boxed()
        .collect(Collectors.toList());
```

这和第 13 课要讲的**线程安全**是同一件事——`ArrayList` 不是线程安全的，
并发 `add` 会丢数据、甚至抛异常。

**并行流的正确姿势**：用 `collect` 而不是 `forEach` 去修改共享状态。
`collect` 的设计（分片 + 合并）本身就是为并行准备的。

## 五、用的是哪个线程池

```terminal
========== 9. 用的是哪个线程池 ==========
  ForkJoinPool.commonPool 的并行度 → 15
  Runtime 报告的 CPU 核数 → 16
  ← 并行度通常等于核数减一（留一个给主线程）
  ← 关键：整个 JVM 共享这一个池，一个并行流卡住会影响别的并行流
```

三个要点：

1. **默认用 `ForkJoinPool.commonPool()`**，并行度默认是 `核数 - 1`
2. **整个 JVM 共享这一个池**。你的两个并行流、以及别处的并行流，
   抢的是同一批线程
3. **可以换池**：把并行流提交到自己建的 `ForkJoinPool` 里执行，
   避免和其他业务互相影响。但这是进阶用法

**第 2 点在生产上很重要**：如果一个并行流里有慢操作（比如 IO），
它会把 commonPool 的线程占住，影响所有其他并行流。

## 六、并行流一定更快吗

**不一定。** 第 10 节：

```terminal
========== 10. 并行流一定更快吗 ==========
  100 个元素：顺序 5050 / 并行 5050  结果一样吗 → true
  ← 数据量小的时候，并行的线程调度开销可能比省下的时间还多
  ← 这里故意不打印耗时：微基准抖动太大，贴出来会误导
```

**这一节我故意没打印耗时数字。** 原因是我实测过：同一份代码跑十次，
结果能差好几倍（受 JIT 预热、GC、系统负载影响）。
贴一个"并行比顺序快 2 倍"的数字出来，是在误导人。

### 该用并行流的情况

| 条件 | 说明 |
|---|---|
| **数据量大** | 通常几万以上才值得，太少的话分片开销都收不回来 |
| **计算密集** | 每个元素都要算一会儿，并行才有意义 |
| **无状态** | 不依赖外部可变状态 |
| **不要求顺序** | 或者用 `forEachOrdered` / `collect` 这种保序的 |

### 不该用的情况

| 情况 | 为什么 |
|---|---|
| 数据量小 | 分片 + 线程调度开销 > 收益 |
| **IO 密集** | 线程都在等 IO，并行不解决问题（应该用异步 IO） |
| 需要顺序 | `forEach` 会乱序 |
| 操作共享可变状态 | 会丢数据 |
| 在 commonPool 里做慢操作 | 会拖累整个 JVM 的其他并行流 |

**一句话**：**别因为"能加 parallel"就加。** 先用顺序流，
确认它是瓶颈、且符合上面的条件，再改成并行，然后**用真实压测验证**。

## 七、不推荐的用法

- **别随手 `.parallel()`**。很多人以为加了就变快，实测经常更慢
- **别在并行流里做 IO**。线程池会被占满，影响全 JVM
- **别用 `forEach` 修改共享集合**。用 `collect`
- **别对非结合性操作用 `reduce`**。顺序流和并行流结果不同
- **别依赖并行流的执行顺序**。除了 `forEachOrdered` 和保序 `collect`，
  其他都不保证
- **别在并行流里嵌套并行流**。都在同一个 commonPool 里，容易死锁式卡住

## 八、这一课的术语表

- **并行流**（parallel stream）—— 把流的数据分片交给多个线程处理
- **`parallel()` / `parallelStream()`** —— 两种创建方式
- **出现顺序**（encounter order）—— 数据源本身的顺序；`forEachOrdered` 保证它
- **`forEachOrdered`** —— 保序执行，牺牲部分并行度
- **分片**（split）—— `Spliterator` 把数据切成多段
- **合并**（combine）—— `combiner` 把各分片的结果按顺序合起来
- **结合律**（associativity）—— `(a op b) op c == a op (b op c)`；
  不满足就不能用于并行 `reduce`
- **`ForkJoinPool.commonPool()`** —— 并行流默认用的共享线程池
- **并行度**（parallelism）—— 池里同时能跑几个任务，默认是核数 - 1
- **弱一致**（weakly consistent）—— 并行处理时看到的可能不是最新状态
