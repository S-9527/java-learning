# 01 · 变量与类型

这一章回答一个问题：**一个变量里到底装着什么**。

看完你应该能解释这些现象：

- 为什么 `7 / 2` 是 3 而不是 3.5
- 为什么 `Integer.MAX_VALUE + 1` 不会报错，而是变成最小值
- 为什么 `==` 比较字符串「有时候能用」

## 基本类型和引用类型

Java 只有两种变量：**8 种基本类型**存值，其余全是引用。

```java
// src: src/main/java/dev/javaquest/basics/variables/VariableDemo.java
int a = 1;              // 值：数字 1 本身
String s = "java";      // 引用：指向「某个装着 java 的对象」
```

8 种基本类型：

| 类别 | 类型 | 大小 | 取值范围 |
|---|---|---|---|
| 整数 | `byte` | 1 字节 | -128 ~ 127 |
| | `short` | 2 字节 | -32,768 ~ 32,767 |
| | `int` | 4 字节 | -2,147,483,648 ~ 2,147,483,647（约 ±21 亿） |
| | `long` | 8 字节 | 约 ±922 京（±9.22 × 10¹⁸） |
| 浮点 | `float` | 4 字节 | 单精度，约 7 位十进制有效数字 |
| | `double` | 8 字节 | 双精度，约 15-16 位十进制有效数字 |
| 字符 | `char` | 2 字节 | 0 ~ 65,535（**无符号**） |
| 布尔 | `boolean` | 规范未固定，实际通常 1 字节 | `true` / `false` |

`float`/`double` 是**近似值**，其余六种是精确的。这是后面很多坑的根源。

日常写代码用得最多的是 `int`、`long`、`double`、`boolean`、`char`。
真正少用的是 `byte`、`short`、`float`：前两个多见于文件格式和协议解析，
`float` 因为精度问题基本只在读别人的数据时才碰。

## 整数除法直接丢余数

Java 不猜你的意图。`/` 两边都是整数，结果就是整数，余数被丢掉，**不做四舍五入**。

`VariableTest#integerDivisionDropsTheRemainder`

```java
7 / 2    // 3，不是 3.5
```

要拿到小数，显式告诉它用浮点：

```java
7 / 2.0      // 3.5   除数是小数，整数被提升
7.0 / 2      // 3.5   被除数是小数，整数被提升
7 / (double) 2   // 3.5   显式转换
7 / 2        // 3     两边都是整数，丢掉余数
```

**负数是向零截断，不是向下取整。** 这是 Java 和 Python 最容易被坑的差别。

`VariableTest#negativeDivisionTruncatesTowardZero`

```java
-7 / 2    // -3，不是 -4
```

Python 里 `-7 // 2` 是 `-4`（向下取整）。Java 向零截断，往上靠。

## 取模的符号跟被除数走

`VariableTest#moduloSignFollowsTheDividend`

```java
7 % 2     // 1
-7 % 2    // -1（不是 1！）
7 % -2    // 1  （不是 -1）
-7 % -2   // -1
```

规律：`%` 结果的符号和**被除数**一致。

这直接影响一个常见写法。`VariableTest#negativeEvenNumberModuloIsZero`

```java
-4 % 2        // 0，不是 1
```

于是判断奇偶就有两种写法：

```java
// 错：n = -4 时，-4 % 2 == 0，所以 isEven 变成 false，负偶数被误判
boolean isEven = n % 2 == 1;

// 对：正负都能正确判断
boolean isEven = n % 2 == 0;
```

`VariableExercisesTest#exerciseEvenCheckThatWorksForNegatives` 就是练这个。

## 溢出是静默的

**Java 里所有整数运算都是静默回绕，不会抛异常。**

`VariableTest#integerOverflowWrapsAroundSilently`

```java
Integer.MAX_VALUE + 1    // Integer.MIN_VALUE，负数！
```

这个坑特别危险，因为编译不报错、运行不报错，只有结果错了。
「查 bug 查到怀疑人生」的现场大概率就是它。

反例：

```java
long big = 9999999999;            // 编译报错：字面量超出 int 范围
long ok  = 9999999999L;           // 加 L 后缀才是 long
long z   = 2147483648L;           // 同上，这是最直接的办法

int  x   = 2147483647 + 1;        // 编译通过，运行结果是 -2147483648
int  y   = 2147483648;            // 编译报错：字面量超出 int 范围
long w   = (long) 2147483647 + 1;  // 先转 long 再加，得 2147483648
```

补一句容易被绕进去的地方：`long w = (int) 2147483648;` 同样编译不过，
但**不是因为转换写错了**，而是 `2147483648` 这个字面量本身就越出了 `int` 范围。
编译器看到数字的那一刻就报 `integer number too large`，跟你后面写什么类型转换无关。

### 除了「加 L」，还有别的护栏

编译期字面量检查只是第一道。真正怕的是**运行时算出来的数溢出**，
因为那类表达式两边都是变量，编译器看不出问题。

`VariableTest#overflowCanBeDetectedOrAvoided`

```java
// 1. 转换类型，从源头避开
long widened = (long) Integer.MAX_VALUE + 1;    // 2147483648

// 2. 主动检测，溢出就抛异常
Math.addExact(a, b);          // ArithmeticException: integer overflow
Math.multiplyExact(a, b);
Math.toIntExact(bigLong);     // long 超出 int 范围时抛异常
```

数值本身可能很大时，用 `long` 或 `BigInteger` 从源头避免溢出。
业务上还要防「结果虽然没溢出但超出合理范围」，那得自己写范围检查——
这类问题编译器永远不会帮你发现。

## byte 相加会变成 int

小于 int 的类型（`byte`、`short`、`char`）参与算术运算时，**先统一提升成 int**。

`VariableTest#byteAdditionPromotesToInt`

```java
byte a = 100;
byte b = 100;
int  c = a + b;      // OK，200
byte d = a + b;      // 编译报错：需要显式转换
```

这不是缺陷，是防错设计。`100 + 100` 的结果塞回 byte 是 200，byte 装不下，
编译器在编译期就拦下来，比运行期溢出强。

顺带：`char` 也是这样，`'A' + 1` 的结果是 int `66`，塞回 `char` 要写 `(char) 66`。

## char 就是个 16 位无符号整数

`VariableTest#charIsAnUnsignedNumber`

```java
(int) 'A'        // 65        char 转 int，得到编码值
'A' + 1          // 66（int）  算术运算的结果类型是 int
(char)('A' + 1)  // 'B'       结果是 int 66，显式转回 char
'a' - 'A'        // 32        大写字母的编码比小写小 32
'A' - 'a'        // -32       顺序反了就是负数
```

小心一个容易写错的：`(char) 'A'` 什么都没做，结果还是 `'A'`。
想把字符换成它的数字，必须转 `int`。

因为 `char` 无符号，它的取值范围是 0 ~ 65,535，和同样 16 位的 `short`
（-32,768 ~ 32,767）正好相反。对应到常量：

```java
Character.MIN_VALUE    // '\u0000'，就是 0
Character.MAX_VALUE    // 65535
```

平时用不到，知道它属于「unsigned」这一类就够了。

## 浮点数天生不精确

**`0.1 + 0.2` 不等于 `0.3`。**

`VariableTest#floatingPointIsNotExact`

```java
0.1 + 0.2 == 0.3                 // false，实际是 0.30000000000000004
0.1 + 0.2 - 0.3 == 0             // false
Math.abs((0.1 + 0.2) - 0.3) < 1e-9  // true，这才是对的比较方式
```

原因：`float`/`double` 用二进制浮点存数，而 `0.1` 在二进制里是无限循环小数，
必须截断。截断之后再相加，误差就留下了。

**结论：浮点数永远不要用 `==` 比较。** 给一个容差：

```java
// AssertJ：within 表达「允许的绝对误差」
assertThat(0.1 + 0.2).isCloseTo(0.3, within(1e-9));

// 同义写法（AssertJ 里 withPrecision 对 double 就是 within 的别名）
assertThat(0.1 + 0.2).isCloseTo(0.3, withPrecision(1e-9));
```

用 `within` 更直白：参数就是「差多少以内算相等」。注意它是**绝对**容差，
所以比较大数量级的数时，`within(1e-9)` 可能比数值本身的误差还小，
那时该按相对误差来定容差，或者干脆改用 `BigDecimal`。

涉及金额的场景，连 `double` 都别用，用 `BigDecimal`（第 8 章会讲）。
`VariableExercisesTest#exerciseComparingFloatingPoint` 是练这个。

## String 不可变，且有常量池

Java 的 `String` 是**不可变**的：任何「修改」都产生新对象，原对象一个字都不动。
加上它是引用类型，就引出了两个经典现象。

**现象一：字面量会共享对象。**

`VariableTest#stringLiteralsShareOneObject`

```java
String a = "java";
String b = "java";
a == b     // true，共用常量池里同一个对象
```

**现象二：`new` 出来的对象内容和字面量一样，但不是同一个。**

`VariableTest#freshlyBuiltStringIsNotTheSameObject`、
`VariableTest#twoBuiltStringsAreContentEqualButNotIdentical`

```java
String a = "java";
String b = new String("java");
a.equals(b)   // true，内容相同
a == b        // false，地址不同

new String("java").equals(new String("java"))   // true，两个手工 new 的对象内容一样
```

> 入门阶段不要写 `new String("...")`：它白白多建一个对象，没有换来任何东西。
> 现实里它偶尔有正当用途——比如你**刻意**要一个不在常量池里的 `String`
> 作为 `HashMap` 的 key，或传给要求「每个 key 都是独立实例」的旧 API。
> 但那是明确场景下的选择，不是随手写的习惯。

**现象三：拼接不动原对象。**

`VariableTest#concatenationLeavesLeftOperandUntouched`

```java
String s = "ab";
String t = s + "c";   // t 是新对象
s                    // 还是 "ab"
```

所以结论很简单：**`==` 比地址，`equals()` 比内容，判字符串内容永远用 `equals()`。**
`String` 已经重写了 `equals()`，直接用就行。

`VariableExercisesTest#exerciseComparingTwoBuiltStrings` 是练这个。

## final 锁引用，不锁内容

`final` 让你**不能再指向别的对象**，但对对象内部的东西一无所知。

`VariableTest#finalLocksTheReferenceNotTheObject`

```java
final List<String> list = new ArrayList<>();
list.add("x");        // 随便加，final 管不着
list = new ArrayList<>();  // 编译报错：不能重新指向

final int n = 5;
// n = 6;             // 编译报错
```

反例：

```java
final User u = new User("张三");
u.setName("李四");    // 编译通过。u 指向的 User 对象被改了，final 完全不知道
```

想让对象整体不可变，就得保证**它内部的引用全是 final，且内部对象也不可变**。
Java 16 起有更简洁的写法 `record`（14/15 版是预览特性），第 6 章会讲。

## 自动装箱和 Integer 缓存

`int` 和 `Integer` 之间会自动转换，这叫装箱/拆箱。

`VariableTest#boxedIntegerIdentityIsCachedUpTo127`、
`VariableTest#boxedIntegerIdentityIsNotCachedAbove127`

```java
Integer a = 127, b = 127;
a == b      // true —— 缓存池

Integer c = 200, d = 200;
c == d      // false —— 超出缓存范围，两个不同对象
c.equals(d) // true
```

缓存范围是 `-128 ~ 127`。这就是为什么 `Integer`/`Long` 等包装类型
**永远不能 `==`**，哪怕值看起来「应该」在缓存里。

顺带一个高频面试题：

```java
Integer i = 127;
i = i + 1;    // 拆箱 → 加法 → 装箱
// i 现在是 128，且是一个新对象
```

```java
Short s = 1;      // 编译报错：int 不能直接装箱成 Short
Integer i = 1;
Long   l = 1;     // 同样编译报错：Integer 不是 Long
```

## 本章要点

- `int` 除法丢余数，负数向零截断
- `%` 的符号跟被除数走
- 整数溢出静默回绕。字面量超范围编译期会拦，但运行时算出来的溢出拦不住——
  用 `Math.addExact()` 主动检测，或一开始就用 `long`
- `byte`/`short`/`char` 参与运算自动提升成 `int`
- 浮点永远不 `==`
- `String` 不可变，判内容用 `equals()`
- `final` 只锁引用
- 包装类型的 `==` 是缓存巧合，永远别用
