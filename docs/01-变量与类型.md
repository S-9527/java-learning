# 01 · 变量与类型

这一章只回答一个问题：**一个变量里到底装着什么**。

答案有两种：**值**，或者**一个地址**。八种基本类型装值，其余一切装地址。

后面所有让人意外的现象，都能从这一句推出来：

- 装着**值**的变量，算出来的结果有时和直觉不一样（整数除法、溢出、浮点精度）
- 装着**地址**的变量，两个"看起来一样"的变量未必相等（`==`、`final`、自动装箱）

# 一、装值的：八种基本类型

| 类别 | 类型 | 大小 | 取值范围 |
|---|---|---|---|
| 整数 | `byte` | 1 字节 | -128 ~ 127 |
| | `short` | 2 字节 | -32,768 ~ 32,767 |
| | `int` | 4 字节 | -2,147,483,648 ~ 2,147,483,647（约 ±21 亿） |
| | `long` | 8 字节 | ±9.22 × 10¹⁸ |
| 浮点 | `float` | 4 字节 | 单精度，约 7 位十进制有效数字 |
| | `double` | 8 字节 | 双精度，约 15-16 位十进制有效数字 |
| 字符 | `char` | 2 字节 | 0 ~ 65,535（**无符号**） |
| 布尔 | `boolean` | 规范未固定，实际通常 1 字节 | `true` / `false` |

日常写代码用得最多的是 `int`、`long`、`double`、`boolean`、`char`。
少用的是 `byte`、`short`、`float`：前两个多见于文件格式和协议解析，
`float` 因为精度问题基本只在读别人的数据时才碰。

除 `float`/`double` 外，这六种存的都是精确值。这个区别决定了下面几节的写法。

## 为什么 `7 / 2` 是 3 而不是 3.5？

因为 `7` 和 `2` 都是整数，`/` 就按整数除法处理：Java 取商，把余数丢掉。
它不猜你是不是想要小数，也不会四舍五入。

```java
7 / 2            // 3
7 / 2.0          // 3.5    除数是小数，整数被提升成 double
7.0 / 2          // 3.5    被除数是小数，整数被提升成 double
7 / (double) 2   // 3.5    显式转换，效果同上
```

想拿小数，让参与运算的**任意一边**是小数就行。

负数的规则是**向零截断**——去掉小数部分往零靠：

```java
-7 / 2    // -3，不是 -4
```

对比一下 Python：`-7 // 2` 是 `-4`（向下取整，往负无穷靠）。
两者的差别在处理负数时才会显现。

对应测试：整数除法丢余数；负数向零截断。练习 1 练取模的符号。

## 为什么 `%` 的结果符号跟着被除数走？

```java
7 % 2     // 1
-7 % 2    // -1
7 % -2    // 1
-7 % -2   // -1
```

规律是：结果的符号和**被除数**一致，除数不影响符号。

这个规律直接影响奇偶判断：

```java
-4 % 2    // 0
```

于是下面两种写法就有了区别：

```java
int n = -4;

boolean isEven = n % 2 == 1;    // false，负偶数被误判成奇数
boolean isEven = n % 2 == 0;    // true，正负都能正确判断
```

对应测试：取模符号跟被除数走；负偶数取模是 0。练习 2 就是练这个。

## 为什么 `Integer.MAX_VALUE + 1` 变成了最小值？

因为整数的运算结果如果超出了类型的范围，会**回绕**到另一端，而不是报错。

```java
int max = Integer.MAX_VALUE;   // 2147483647
int wrapped = max + 1;         // -2147483648
```

从二进制角度看这是一回事：8 位的 `1111 1111` 加一变成 `0000 0000`，
每一位都还在，只是没有进位能承载。

编译器在**字面量**层面会帮你拦一道：

```java
long big = 9999999999;      // 编译报错：字面量超出 int 范围

long ok = 9999999999L;      // 加 L 后缀，或者直接写成一个不会溢出的 long
long z  = 2147483648L;      // 同上

int  x = 2147483647 + 1;    // 编译通过，运行结果是 -2147483648
int  y = 2147483648;        // 编译报错：字面量超出 int 范围

// 想要 2147483648，先把其中一个操作数变成 long，整条表达式就都在 long 里算
long base = 2147483647L;
long w = base + 1;          // 2147483648
```

一个容易绕进去的地方：`long w = (int) 2147483648;` 同样编译不过，
但原因不是转换写错了，而是 **`2147483648` 这个字面量本身就超出了 `int`**。
编译器看到数字的那一刻就报 `integer number too large`，跟你后面写什么转换无关。

### 运行时算出来的溢出，编译器管不了

字面量检查只覆盖「数字直接写出来」的情况。真正需要留意的是**变量之间的运算**——
两边都是变量时，编译器看不出结果会不会超范围。

两种应对方式：

```java
// 1. 转换类型，从源头避开
long base = 2147483647L;
long widened = base + 1;       // 2147483648

// 2. 主动检测，越界就抛异常
Math.addExact(a, b);           // ArithmeticException: integer overflow
Math.multiplyExact(a, b);
Math.toIntExact(bigLong);      // long 超出 int 范围时抛异常
```

数值本身可能很大时，直接用 `long` 或 `BigInteger`。
还有一类问题是编译器永远不会帮你发现的：**结果没溢出，但超出了业务上合理的范围**
（比如年龄算出来是 200）。那只能自己写范围检查。

对应测试：溢出静默回绕；溢出可检测或可规避。练习 5 就是练第 1 种做法。

## 比 `int` 小的类型：`byte`、`short`、`char`

这三种类型参与算术运算时，会**先统一提升成 `int`**，然后用 `int` 完成运算。
这是防错设计——提升后结果塞不回原类型时，编译器在编译期就拦住了。

**`byte` 和 `short` 的提升：**

```java
byte a = 100;
byte b = 100;

int  c = a + b;      // OK，200
byte d = a + b;      // 编译报错：需要显式转换
```

`100 + 100` 的结果塞回 `byte` 是 200，而 `byte` 装不下。

**`char` 的提升：**

```java
(int) 'A'        // 65        想拿到字符的数字，要转 int
'A' + 1          // 66（int） 运算结果类型是 int
(char)('A' + 1)  // 'B'       结果是 int 66，显式转回 char
```

顺便注意一个容易写错的：`(char) 'A'` 什么都没做，结果还是 `'A'`。
想把字符换成它的数字，必须转 `int`。

**`char` 还是 16 位无符号整数**，所以取值范围是 0 ~ 65,535，
和同样 16 位的 `short`（-32,768 ~ 32,767）正好相反：

```java
Character.MIN_VALUE    // '\u0000'，就是 0
Character.MAX_VALUE    // 65535

'a' - 'A'    // 32    大写字母的编码比小写小 32
'A' - 'a'    // -32   同样的差，符号相反
```

大小写转换、判断是不是数字这类操作，底层就是这两个数相减。

对应测试：byte 相加提升成 int；char 是无符号整数。练习 6 练两个字符相减。

## 为什么 `0.1 + 0.2` 不等于 `0.3`？

因为 `float`/`double` 存的是**近似值**。

```java
0.1 + 0.2 == 0.3                        // false，实际是 0.30000000000000004
0.1 + 0.2 - 0.3 == 0                    // false
Math.abs((0.1 + 0.2) - 0.3) < 1e-9       // true
```

原因是 `0.1` 在二进制里是无限循环小数（0.0001100110011...），
必须截断到有限位。截断之后再相加，误差就留下了。

所以比较浮点数要给一个容差：

```java
// AssertJ：within 表达「允许的绝对误差」
assertThat(0.1 + 0.2).isCloseTo(0.3, within(1e-9));

// 同义写法：AssertJ 里 withPrecision 对 double 就是 within 的别名
assertThat(0.1 + 0.2).isCloseTo(0.3, withPrecision(1e-9));
```

用 `within` 更直白：参数就是「差多少以内算相等」。注意它是**绝对**容差，
所以比较 1e6 这种大数量级时，`within(1e-9)` 可能比数值本身的误差还小，
那时需要按相对误差来定容差。

涉及金额的场景用 `BigDecimal` 而不是 `double`（第 8 章会讲）。

对应测试：浮点数天生不精确。练习 3 练怎么写这个断言。

# 二、装地址的：其余一切

八种基本类型之外的所有变量，装的都是**地址**。
这一节的现象都源于同一件事：地址能一样，内容也能一样，但两者不是一回事。

## 为什么 `==` 比较字符串「有时候能用」？

```java
String a = "java";
String b = "java";
a == b     // true
```

两个变量指向**同一个对象**，因为字面量 `"java"` 在常量池里只有一份，
两边拿到的都是它的地址。

但换成 `new` 就不一样了：

```java
String a = "java";
String b = new String("java");

a.equals(b)   // true，内容相同
a == b        // false，地址不同
```

`==` 比的从来是地址，`equals()` 比的才是内容。字面量能「凑巧」用 `==`，
是因为常量池恰好让它们指向同一个对象——那是巧合，不是规则。

结论：**判字符串内容用 `equals()`**。`String` 已经重写了 `equals()`，直接用就行。

对应测试：字面量共享同一个对象；手工 new 的内容相同但不同一；两个 new 的内容相等。

> 入门阶段不需要写 `new String("...")`：它多建一个对象，没有换来任何东西。
> 现实里它偶尔有正当用途——比如你**刻意**要一个不在常量池里的 `String`
> 作为 `HashMap` 的 key，或传给要求「每个 key 都是独立实例」的旧 API。
> 但那是明确场景下的选择，不是随手写的习惯。

## 为什么拼接不改动原来的字符串？

因为 `String` 是**不可变**的：任何「修改」都产生新对象，原对象一个字都不动。

```java
String s = "ab";
String t = s + "c";   // t 是新对象
s                     // 还是 "ab"
```

这也是为什么 `s + "c"` 不能用来「修改」一个字符串——你拿到的是新对象，
原来的那个还在原地。变量一旦指向引用，「看起来在改」和「真的在改」就分开了。

对应测试：拼接不会改动左边的对象。练习 4 从另一个角度练同一件事。

## `final` 锁住了什么？

`final` 让你**不能再指向别的对象**，但对对象内部的内容一无所知。

```java
final List<String> list = new ArrayList<>();
list.add("x");            // 可以随意添加
list = new ArrayList<>(); // 编译报错：不能重新指向

final int n = 5;
// n = 6;                  // 编译报错
```

对基本类型来说这两者是同一件事——`final int` 就是「值不能再变」。

但对对象来说，「指向哪个对象」和「对象里有什么」是两件事：

```java
final User u = new User("张三");
u.setName("李四");    // 编译通过。u 指向的 User 被改了，final 管不到
```

想让对象整体不可变，需要保证**它内部的引用全是 `final`，且内部对象本身也不可变**。
Java 16 起有更简洁的写法 `record`（14/15 版是预览特性），第 6 章会讲。

对应测试：final 锁的是引用不是内容。

## 为什么 `Integer` 也能用 `==` 比较了？

`int` 和 `Integer` 之间会自动转换，叫装箱和拆箱。装箱之后，
装的就从「值」变成了「对象」——于是 `==` 的含义也跟着变了。

```java
Integer a = 127, b = 127;
a == b       // true —— 小整数有缓存池，两次装箱拿到同一个对象

Integer c = 200, d = 200;
c == d       // false —— 超出缓存范围，是两个对象
c.equals(d)  // true
```

缓存范围是 `-128 ~ 127`。127 之所以能用 `==`，纯粹因为它落在缓存里。

所以包装类型（`Integer`、`Long`、`Double`…）一律用 `equals()` 或 `intValue()`，
**不要用 `==`**。哪怕值看起来"应该"在缓存范围内也别赌——把常量改成配置项就翻了。

顺带两个常见现象：

```java
Integer i = 127;
i = i + 1;     // 拆箱 → 加法 → 装箱，i 变成 128，是一个新对象
```

```java
Short s = 1;        // 编译报错：int 不能直接装箱成 Short
Integer i = 1;
Long l = 1;         // 编译报错：Integer 不是 Long
```

对应测试：装箱缓存范围内复用同一对象；超出缓存不复用。

## 本章要点

回到开头那句话：**变量里装的是值，或者一个地址。**

装值的那一侧：

- 整数除法丢余数，负数向零截断
- `%` 的符号跟被除数走
- 整数溢出会回绕。字面量超范围编译期会拦，运行时算出来的拦不住——
  用 `Math.addExact()` 检测，或一开始就用 `long`
- `byte`/`short`/`char` 参与运算自动提升成 `int`；`char` 无符号
- `float`/`double` 是近似值，比较要给容差

装地址的那一侧：

- `String` 不可变，任何「修改」都产生新对象
- `==` 比地址，`equals()` 比内容，判内容用 `equals()`
- `final` 锁的是指向，不是内容
- 装箱让「值」变成「对象」，包装类型一律用 `equals()`
