## 一、先让代码疼一次：调了 `run()`，其实没开线程

假设你要干两件事：一件 2 秒，一件 1 秒。串着做就是 3 秒，你想让它们同时干。

于是你写了这么一段——很自然的写法，`Thread` 也 `new` 了，`run()` 也调了：

```java
Thread t = new Thread(() -> System.out.println(
        "run() 里打印的线程名 = " + Thread.currentThread().getName()), "worker");

t.run();      // ← 我调了 run()，它应该在新线程上跑吧？
```

跑一下，问题立刻现形：

```terminal
直接调 t.run()：
    run() 里打印的线程名 = main
  上面打印的是 main —— 根本没有新线程
```

**`run()` 里打印的是 `main`。**

`Thread` 对象是造出来了，`run()` 里的代码也确实跑了，但它跑在**当前线程**上——
对你来说就是 `main` 线程。`t.run()` 从头到尾只是一次普普通通的方法调用，
跟你调 `list.add()` 没有任何区别。新线程？影子都没有。

这个坑的隐蔽之处在于：**代码不报错，结果也"对"**（那行字确实打印了），
只是你想要的并发完全没发生。等你在生产环境发现"我明明开了线程怎么还是慢"，
就已经很晚了。

那么问题就来了：**怎样才能真的开一个新线程？**

## 二、正解：`start()` 才是开线程

把上面那句 `t.run()` 换成 `t.start()`，别的都不动：

```java
t.start();    // ← 这才是「开一个新线程」
```

```terminal
再调 t.start()：
    run() 里打印的线程名 = worker
  同一段 run()，start() 之后就跑到 worker 上了
```

同一段 `run()` 方法体，`start()` 之后就跑到 `worker` 上了。

两个方法的分工，一次说清：

| | 干了什么 | 跑在哪个线程 | 能调几次 |
|---|---|---|---|
| `run()` | 就是普通方法调用，执行方法体 | **当前线程**（谁调谁跑） | 想调几次调几次 |
| `start()` | 让 JVM 创建一个新线程，由它去调 `run()` | **新线程** | 只能一次 |

`start()` 第二次会抛 `IllegalThreadStateException`——一个 `Thread` 对象一辈子只能启动一次。
想再跑一遍，得重新 `new` 一个。

### 2.1 并发和并行不是一回事

在往下走之前，先把两个天天被混用的词分开。

- **并发 Concurrency**：同一**时间段**内处理多个任务。靠 CPU 调度快速切换，
  让你感觉它们是同时在跑。**单核也能并发**——逻辑上同时，物理上轮流。
- **并行 Parallelism**：同一**时刻**真的在跑。这个需要多核，单核做不到。

上一课的 `parallelStream()` 要的是并行；而"一边下载一边让界面能点"，
单核上靠并发就够了。

```terminal
并发 Concurrency：同一时间段内处理多个任务，靠调度快速切换
                  单核也能并发 —— 逻辑上同时，物理上轮流
并行 Parallelism：同一时刻真的在跑，需要多核
你机器有几个核，决定了「并发」能不能变成真的「并行」
（Runtime.getRuntime().availableProcessors() 能查到，这个数随机器变，本课不打印它）

-- 两个任务在同一段时间里交替推进
  A 第 1 次推进
  B 第 1 次推进
  B 第 2 次推进
  A 第 2 次推进
  B 的两次都在 A 的两次之间 —— 它们在同一段时间里各自推进
```

`A` 和 `B` 各自推进了两次，`B` 的两次都夹在 `A` 的两次中间。它们就是在这段时间里
**交替**着走的——这就是并发。至于它们到底有没有真的同时跑，取决于你机器有几个核。

**线程**（Thread）是操作系统调度的最小单位。它比进程轻：同一进程里的线程共享内存和
文件句柄，所以切换和通信都便宜得多。代价是——共享的东西谁都能改，这是
[线程安全与同步](./13-线程安全与同步.md)要解决的麻烦。

### 2.2 主线程

JVM 启动时会自动创建一个线程，由它去执行 `main` 方法。它的名字就叫 `main`：

```terminal
执行 main 的线程：main
（还有个 threadId()，是个 JVM 内部编号，随机器变，这里不打印）
启动之前叫：worker-1
setName 之后叫：搬砖工
  线程里看到自己的名字 = 搬砖工
```

`Thread.currentThread()` 拿到当前线程，`setName()` 改名字。**改名字不影响任何行为**，
它的唯一用处是让你在日志、`jstack`、调试器里认得出是谁在干活——线程一多，
这个用处就大了。

### 2.3 创建线程的四种方式

```terminal
  继承 Thread：run() 跑在 extends-thread 上
  写法最直接，但任务逻辑写死在类里，而且 Java 不支持多继承，扩展性差
  实现 Runnable：同一个任务对象 跑在 worker-1 上
  实现 Runnable：同一个任务对象 跑在 worker-2 上
  任务和线程解耦了：一个 Runnable 对象可以被多个线程执行
  Lambda 版：跑在 lambda-worker 上
  不给名字的线程，JVM 自动叫它：Thread-0
  编号按「创建顺序」发，本课其余地方都显式命名，所以这里每次都是 Thread-0
  还没跑完时 isDone() = false
  get() 拿到的结果 = Callable 的返回值（来自 callable-worker）
  跑完之后 isDone() = true
  get() 抛了 ExecutionException，真正的原因在 getCause() 里：Callable 里可以抛异常
  这是线程池那一课的主角，这里先见个面
```

**方式一：继承 `Thread`，重写 `run()`**

```java
static class NamedTask extends Thread {
    NamedTask(String name) { super(name); }

    @Override
    public void run() {
        System.out.println("...");
    }
}
```

写法最直接，但毛病明显：任务逻辑写死在类里，而且 **Java 不支持多继承**。
`NamedTask` 一旦 `extends Thread`，就再也没法继承别的类了。扩展性差。

**方式二：实现 `Runnable`（推荐）**

```java
static class PrintTask implements Runnable {
    @Override
    public void run() { ... }
}
```

`PrintTask` 只是一个普通类，不是线程。上面输出里 `worker-1` 和 `worker-2` 跑的是
**同一个** `PrintTask` 对象——这就是解耦的价值：**任务和线程分开，一个任务对象
可以被多个线程执行**。

**方式三：Lambda**

`Runnable` 是函数式接口（只有一个抽象方法 `run`），所以[Lambda 表达式](./07-Lambda表达式.md)直接能用：

```java
new Thread(() -> System.out.println("..."), "lambda-worker")
```

实际写代码时，**九成以上都是这一种**。

**方式四：`Callable` + `FutureTask`**

前三种的 `run()` 都没有返回值，也不能抛受检异常。`Callable` 两样都行：

```java
FutureTask<String> task = new FutureTask<>(() -> {
    Thread.sleep(200);
    return "Callable 的返回值";
});
new Thread(task, "callable-worker").start();
task.get();     // 拿到返回值，会阻塞到算完
```

`get()` 拿到结果；`Callable` 里抛的异常会被包进 `ExecutionException`，
真正的原因在 `getCause()` 里。

不过 `Callable` 真正的舞台是**线程池**——你不会真的为每个任务 `new` 一个 `Thread`。
这里先见个面，细节留到[线程池](./17-线程池.md)那一课。

四种方式怎么选：

| 方式 | 能返回结果 | 能抛受检异常 | 任务和线程解耦 | 什么时候用 |
|---|---|---|---|---|
| `extends Thread` | ❌ | ❌ | ❌ | 基本不用，认识就行 |
| `implements Runnable` | ❌ | ❌ | ✅ | 需要写成具名类时 |
| Lambda | ❌ | ❌ | ✅ | **默认选它** |
| `Callable` + `FutureTask` | ✅ | ✅ | ✅ | 要返回值时（线程池里更常见） |

## 三、线程是异步的，`join()` 是"等"

### 3.1 主线程不会等子线程

`start()` 一调完就立刻返回，主线程接着往下走。子线程在背后自己跑：

```terminal
主线程：子线程已经启动，但我不等它
主线程：我自己的活已经干完了
主线程：上面这两行都排在子线程那一行前面 —— 谁也没等谁
子线程：我睡醒了，现在才轮到我的输出
主线程：这一节末尾我 join 了一下，纯属为了排版整齐
```

主线程那三行**全部**排在子线程那行前面。子线程明明被启动了，主线程却一眼都没回头看它。

这就是"异步"：**发起**和**完成**是两件事。上一课并行流的结果乱序，
根子就在这里——多个线程各跑各的，谁先谁后由调度器决定。

### 3.2 `join()`：等另一个线程做完

想让主线程等一等，就调 `join()`：

```terminal
  主线程：调 join() 之前
  主线程：下面这行 join() 会把我卡住
  子线程：开始干活
  子线程：干完了
  主线程：join() 返回了，说明子线程已经结束
    A：我要等 B，所以我先卡住
    B：我结束了
    A：B 结束了，我接着跑
    main：我只等了 A，B 是 A 等的
```

关键是这句话：

> **`join()` 阻塞的是「调用它的那个线程」，不是「被 join 的线程」。**

- 在 `main` 里调 `t.join()` → 卡住的是 `main`
- 在 `A` 线程里调 `b.join()` → 卡住的是 `A`

上面第二个实验就是后者：`A` 去等 `B`，`main` 只等 `A`。输出里 `B` 先结束，
然后 `A` 才继续——但 `main` 并没有被 `B` 卡住。

### 3.3 两个线程重叠跑 vs 一个一个跑

这是这一课最值钱的一个实验。**都是"开了两个线程"，效果却完全不同。**

```terminal
-- 方式一：两个都 start，再依次 join
  A 开始（要 900ms）
  B 开始（要 400ms）
  B 结束
  A 结束
  B 开始的时候 A 还没结束 —— 两个线程是重叠跑的
  总耗时约 900 ms，比 900 + 400 = 1300 少
-- 方式二：启动一个、join 一个，再启动下一个
  A 开始（要 900ms）
  A 结束
  B 开始（要 400ms）
  B 结束
  A 结束之后 B 才开始 —— 严格串行
  总耗时约 1300 ms，差不多是 900 + 400
  注意：join() 只是「等」，不是「排队」。线程一旦 start 就已经在跑了
```

方式一是**先都 `start()`，再依次 `join()`**：两个线程在 900ms 那段时间里重叠，
总耗时约 900ms（不是 1300ms）。

方式二是**启动一个 `join()` 一个，再启动下一个**：`B` 要等 `A` 完全结束才出生，
严格串行，总耗时约 1300ms。

所以还有一句要记住：

> **`join()` 不会"控制线程的并发行为"。线程一旦 `start()` 就已经在跑了，
> `join()` 只是"等"，不是"排队"。**

想串行就别开两个线程——开了再想用 `join()` 把它们"排"起来，
只会白等一遍。

### 3.4 关于输出稳定性（这一课最容易翻车的地方）

线程的输出顺序天生不确定，所以这一课的 demo 做了不少手脚，值得单独说明白：

- **凡是要讲先后顺序的地方，都用了 `join()` / `CountDownLatch` / `sleep()` 把顺序钉死。**
  比如 3.1 里子线程先 `sleep(800)`，主线程那几行才一定排在前面。
- **真正会抖的数字干脆不打印。** 比如"计数线程数了多少下"，每次都不一样，
  输出里只写"数了多少下每次都不同"。
- **耗时只报个约数。** 3.3 的 `900ms` / `1300ms` 是四舍五入到 100ms 的结果，
  真实毫秒数每次都会抖几十毫秒。
- **有一处确实无法稳定，我们反过来利用它。** 第 2.3 节那个不给名字的线程，
  JVM 按创建顺序编号（`Thread-0`、`Thread-1`……）。因为 demo 里别的地方都显式命名了，
  所以它每次都是 `Thread-0`——但**编号本身是全局计数器**，
  你要是往前面插几行 `new Thread()`，它就会变。
- **守护线程那一节差点翻车，详见第五节。** 那是个真实的教训。

判断一个多线程输出稳不稳，就看它有没有"两个线程抢同一个位置"。有，就一定会抖。

## 四、线程的生命周期六种状态

`Thread.getState()` 返回一个 `Thread.State` 枚举，一共六个值：

```terminal
Thread.State 一共六个值：
  NEW
  RUNNABLE
  BLOCKED
  WAITING
  TIMED_WAITING
  TERMINATED
没有 RUNNING —— 真正在跑的时候，状态也是 RUNNABLE
```

一张表把它们串起来：

| 状态 | 什么时候 | 怎么进去 | 怎么出来 |
|---|---|---|---|
| `NEW` | 造出来了，还没 `start()` | `new Thread(...)` | 调 `start()` |
| `RUNNABLE` | 正在跑，或者准备好随时跑 | `start()` | 被调度、去 sleep、去等锁 |
| `BLOCKED` | 等一把锁 | 抢 `synchronized` 没抢到 | 拿到锁 |
| `WAITING` | 无限期地等 | `wait()` / `join()` / `park()` | 被别人唤醒 |
| `TIMED_WAITING` | 有期限地等 | `sleep(ms)` / `join(ms)` | 睡够 / 被唤醒 |
| `TERMINATED` | 跑完了 | `run()` 正常返回或抛异常 | 回不去了 |

demo 里是用**轮询**实时观察的：拿 `getState()` 跟上次比，**只在变化时打印**，
所以输出里刚好是那几次跃迁：

```terminal
start 之前：NEW
状态变成　：RUNNABLE
状态变成　：TIMED_WAITING
状态变成　：TERMINATED
结束之后　：TERMINATED
```

两个重点：

**Java 没有单独的 `RUNNING` 状态。** 真正在跑的时候，状态也是 `RUNNABLE`。
`RUNNABLE` 的含义是"可运行的"——可能正在 CPU 上跑，也可能在等 CPU 的时间片，
Java 不区分这两种。所以**光看状态看不出它是不是正在占用 CPU**。

**`BLOCKED` 和 `WAITING` 这一课不演示。** 它们要等锁和线程通信才出得来，
分别属于[线程安全与同步](./13-线程安全与同步.md)和[线程通信](./16-线程通信.md)那两课。
这里先把名字记住，知道有这两个状态就够了。

## 五、主线程结束 ≠ 进程退出，用户线程 vs 守护线程

### 5.1 只要还有用户线程在跑，JVM 就不退出

先做个小实验。这个实验**必须让 `main` 真的返回**才能看出效果，所以它单独一个类
[`MainExitDemo.java`](../src/main/java/dev/javalearning/concurrency/threads/MainExitDemo.java)：

```terminal
$ java src/main/java/dev/javalearning/concurrency/threads/MainExitDemo.java
[main] 执行 main 的线程叫：main
[main] 子线程启动了
[main] 我不 join，我直接返回
[main] main 方法到此结束
[子线程] 主线程早就返回了，我还在跑
[子线程] 我结束了，JVM 现在才退出
```

最后两行是 `main` **返回之后**才打印的。`main` 早就说"我结束了"，
可 JVM 一直在那儿等着，直到子线程也说完最后一句话，进程才退出。

结论：

> **JVM 退出的条件是「所有用户线程都结束了」，不是「`main` 返回了」。**

### 5.2 守护线程：JVM 退出的最后一块拼图

线程分两种：

- **用户线程**（user thread）：默认创建的都是这种。JVM 必须等它跑完。
- **守护线程**（daemon thread）：`setDaemon(true)` 设成这种。
  **所有用户线程结束时，JVM 直接退出，守护线程被强制终止。**

```terminal
$ java src/main/java/dev/javalearning/concurrency/threads/DaemonExitDemo.java
[守护线程] 第 1 次心跳
[用户线程] 我干完了，我是用户线程
[main] 用户线程结束了，现在只剩守护线程
[main] 我结束了 —— JVM 这就退出，守护线程被直接掐掉
[main] 所以第 2 次心跳永远不会出现
```

看仔细：守护线程打印了**第 1 次**心跳，然后**再也没有第 2 次**。
它那个 `while (true)` 死循环根本没机会再转一圈——JVM 用户线程一清零，
就把它连同进程一起掐了。

对比一下 5.1：`MainExitDemo` 里那个子线程是**用户线程**，JVM 老老实实等到它结束；
`DaemonExitDemo` 里这个是**守护线程**，JVM 说走就走。

用途就是那些"服务型"的后台任务：**GC、日志刷盘、监控上报**。
它们的作用是伺候用户线程，用户线程都没了，它们也就没有存在的意义了。

### 5.3 这里差点翻车：一个真实的教训

`DaemonExitDemo` 我第一版是这么写的：守护线程每 200ms 打一次心跳，
用户线程睡 600ms 之后宣告结束。跑起来看着挺好。

然后我连跑了几次，其中一次是：

```terminal
[守护线程] 第 1 次心跳
[守护线程] 第 2 次心跳
[用户线程] 我干完了，我是用户线程
[main] 用户线程结束了，现在只剩守护线程
[main] 我结束了 —— JVM 这就退出，守护线程被直接掐掉
[守护线程] 第 3 次心跳      ← 这次多出来一行！
```

那一次多打了一行。原因不复杂：用户线程结束时，守护线程可能正好在
**打印和下一次 sleep 之间**，JVM 还没来得及退出，它就把这一行吐出来了。
心跳间隔只有 200ms，这个窗口相对太大。

改法是两条，都很土但很有效：

1. **让守护线程先打印、再计数**，用户线程等到计数才走。这样"第 1 次心跳"
   一定排在"用户线程干完了"前面，不靠 `sleep` 猜。
2. **把心跳间隔拉大到 1500ms**，而用户线程 300ms 就结束。中间这 1200ms 的余量，
   保证 JVM 一定来得及退出，不会冷不丁多冒一次心跳。

改完连跑 10 次，输出的指纹（`md5sum`）完全一样。

**这个教训比结论本身值钱**：多线程的"看起来稳定"和"真的稳定"是两回事。
一个十次里只错一次的输出，肉眼是看不出来的，必须反复跑。
本课所有贴进文档的输出，都是这么验过的。

### 5.4 `setDaemon` 的一个细节

`setDaemon(true)` 必须在线程**还活着之前**调。但拦住你的条件比想象的细——
是 `isAlive()`，**不是"有没有 `start()` 过"**：

```java
Thread dead = new Thread(() -> { });
dead.start();
dead.join();
dead.getState();          // TERMINATED，已经死了
dead.setDaemon(true);     // 不抛异常！标志确实改了
dead.isDaemon();          // true —— 可是线程早死了，毫无意义
```

线程已经结束后再调，它一声不吭地改掉标志。这个行为是测试写出来才发现的，
我原本以为"start 之后一律抛异常"。真实代码别这么写——**设 daemon 就放在
`start()` 前面那一行**，别给自己留悬念。

## 六、中断：`interrupt()` 不是强制停止

### 6.1 Java 没有安全强杀线程的方法

很多语言有"杀掉一个线程"的 API。**Java 没有**——这是故意的。

被废弃的 `stop()` 会在**任意一个字节码位置**强行终止线程。如果那个线程正改到一半
共享数据，它就带着**不一致的状态**死掉了：转账扣了钱没加钱、锁没释放、
文件写了一半。这种 bug 极难查，所以 `stop()` 的下场很彻底，见第七节。

那想停一个线程怎么办？**让它自己停。**

### 6.2 `interrupt()` 只是发一个信号

```terminal
  主线程：调 interrupt() 之前，它活着吗 = true
  主线程：interrupt() 调完了，它立刻返回 —— 这个方法不阻塞
  主线程：中断标志已经置上了 = true
  主线程：可它还在跑，isAlive() = true —— 信号收到了，但没人理
  计数线程：我自己跑满了 1.2 秒才停，全程没人理中断
  主线程：join() 之后才是真的结束，isAlive() = false
  主线程：它数了很多下（具体数字每次都不同，所以不打印）
```

看这几行的顺序：

```terminal
  主线程：interrupt() 调完了，它立刻返回 —— 这个方法不阻塞
  主线程：中断标志已经置上了 = true
  主线程：可它还在跑，isAlive() = true —— 信号收到了，但没人理
```

主线程 `interrupt()` 之后，中断标志确实是 `true`，可那个线程**还在跑**——
因为它的循环里根本没人看这个标志。信号送到了，收件人不在。

所以：

> **`interrupt()` 只是给线程设置一个「中断标志」，停不停由线程自己决定。**

还有个容易忽略的点：**`interrupt()` 是非阻塞的**，调完立刻返回。
它不会等对方真的停下来。所以"中断之后立刻查 `isAlive()` 还是 `true`"是**正常的**，
不是失败——要确认它真结束了，得配合 `join()`。

### 6.3 正确做法一：循环里检查标志

```java
while (!Thread.currentThread().isInterrupted()) {
    // 干活
}
// 跳出循环，自己收场
```

```terminal
  检查标志的线程：看到中断标志了，我自己退出（数了多少下每次都不同，所以不打印）
  主线程：join 之后 isAlive() = false —— 它是自己退出的，没人强杀它
```

### 6.4 正确做法二：接住 `InterruptedException`

如果线程正卡在 `sleep` / `wait` / `join` 上，`interrupt()` 会让它抛
`InterruptedException` 醒过来：

```terminal
  睡觉的线程：被 InterruptedException 吵醒了
  睡觉的线程：catch 里 isInterrupted() = false —— 标志被清掉了
  睡觉的线程：我退出
  主线程：它被吵醒之后就结束了，isAlive() = false
```

注意那句 `catch 里 isInterrupted() = false`——**抛异常的同时，JVM 已经把中断标志清掉了**。
这是 `InterruptedException` 的规矩：异常本身就是"你被中断了"这个信息，
标志就没必要留着了。

所以接住异常之后有两条路：

```java
// 路一：我处理完了，到此为止，退出
catch (InterruptedException e) {
    return;
}

// 路二：我处理不了，把标志放回去，让上层决定
catch (InterruptedException e) {
    Thread.currentThread().interrupt();   // ← 恢复标志
}
```

**别什么都不做**——那叫吞掉中断，见第七节。

### 6.5 `interrupted()` 和 `isInterrupted()` 差一个字母，差很多

```terminal
  刚进来：isInterrupted() = false
  interrupt() 之后：isInterrupted() = true
  Thread.interrupted() 第一次 = true（读到了，顺便把标志清掉）
  Thread.interrupted() 第二次 = false（已经清掉了）
  isInterrupted() = false（它只读，不清）
  一句话：interrupted() 会清除标志，isInterrupted() 不会
```

| 方法 | 谁的方法 | 读标志 | 读完之后 |
|---|---|---|---|
| `isInterrupted()` | 实例方法，`t.isInterrupted()` | ✅ | **不动标志** |
| `interrupted()` | **静态**方法，`Thread.interrupted()` | ✅ | **清除标志** |

`Thread.interrupted()` 是"读并清"，所以连着调两次，第一次 `true`、第二次 `false`。
这也是为什么 6.4 里要"恢复标志"必须用 `interrupt()` 而不能用 `interrupted()`。

记忆法：`interrupted()` 少了个 `is`，也少了个"保持不变"。

## 七、不推荐的用法

### 7.1 `stop()`：在 JDK 25 上直接抛异常

`stop()` 废弃了很多年，现在连"废弃"都不是了——`@Deprecated(since = "1.2", forRemoval = true)`，
**标记为待移除**。那到底还能不能调？跑一下
[`StopIsGoneDemo.java`](../src/main/java/dev/javalearning/concurrency/threads/StopIsGoneDemo.java)：

```terminal
$ java src/main/java/dev/javalearning/concurrency/threads/StopIsGoneDemo.java
src/main/java/dev/javalearning/concurrency/threads/StopIsGoneDemo.java:29: warning: [removal] stop() in Thread has been deprecated and marked for removal
            t.stop();
             ^
1 warning
stop() → java.lang.UnsupportedOperationException
join(300) 之后 isAlive() = true —— 它根本没被停掉
它还在空转，JVM 不会退出，所以这里手动收尾
javac 会警告：[removal] stop() in Thread has been deprecated and marked for removal
```

（除了开头那行命令，前面那段是 `javac` 打在 stderr 上的警告，
`[removal]` 就是"待移除"的意思。）

**两个发现，都跟我原本的预期不一样：**

1. 我以为会像其他废弃方法那样"只是警告，照常工作"。实际上
   **调用直接抛 `UnsupportedOperationException`**——它已经是个空壳了。
2. 更意外的是：抛了异常之后，那个线程**还活着**（`isAlive() = true`）。
   它还在那儿空转，`join(300)` 等不回来，JVM 也不会退出。
   所以这个 demo 最后必须 `System.exit(0)` 收尾。

也就是说，**Java 里现在连"调用会报错的强杀"都没有了**。唯一的路是让线程自己停。

### 7.2 `suspend()` / `resume()`：已经被删掉了

这对方法的问题更严重：`suspend()` 挂起线程时**不释放它手里的锁**，
别的线程一等就是死等；而 `resume()` 要是比 `suspend()` 先到，线程就永远醒不过来。
JDK 把它们**直接删了**——不是废弃，是删掉：

```terminal
$ javac -encoding UTF-8 -d out -sourcepath src/main/java \
    src/main/java/dev/javalearning/concurrency/threads/broken/SuspendResume.java
src/main/java/dev/javalearning/concurrency/threads/broken/SuspendResume.java:20: error: cannot find symbol
        t.suspend();
         ^
  symbol:   method suspend()
  location: variable t of type Thread
src/main/java/dev/javalearning/concurrency/threads/broken/SuspendResume.java:21: error: cannot find symbol
        t.resume();
         ^
  symbol:   method resume()
  location: variable t of type Thread
2 errors
```

`cannot find symbol: method suspend()`——编译器根本找不到这个方法。
这个反面教材在
[`SuspendResume.java`](../src/main/java/dev/javalearning/concurrency/threads/broken/SuspendResume.java)，
它住在 `broken/` 包里，**标红是正常的**。

### 7.3 直接调 `run()` 以为开了新线程

就是第一节那个坑。代码不报错、输出看着也对，只是并发根本没发生。
记住：**要新线程就 `start()`**。

### 7.4 忽略 `InterruptedException`

```java
try {
    Thread.sleep(10_000);
} catch (InterruptedException e) {
    // 什么都不做
}
```

```terminal
  被 interrupt() 之后它还在睡：isAlive() = true（catch 里什么都没做，信号被吞了）
  正确做法：要么在 catch 里退出，要么 Thread.currentThread().interrupt()
  把标志放回去，交给上层处理
```

`catch` 里什么都不做，等于**把中断信号吞了**。上面输出里，线程被 `interrupt()`
之后还在睡——循环接着睡下一个 10 秒，一直睡下去。想停它的人完全失去了控制。

正确做法就 6.4 那两条：**要么退出，要么 `Thread.currentThread().interrupt()`
把标志放回去**。

还有一个容易忽略的细节：`catch` 里只写一句日志、不恢复标志，也是吞——日志打完了，
上层还是不知道要停。

### 7.5 顺带一句：别为每个任务 `new Thread()`

这一课所有例子都 `new Thread(...)`，是为了把概念讲清楚。**真实代码里不要这么写。**
线程的创建和销毁都不便宜，任务一多就会把资源吃光。该用[线程池](./17-线程池.md)——
那是后面某一课的主角。

## 八、这一课的术语表

- **并发**（concurrency）—— 同一时间段内交替处理多个任务，单核也能做
- **并行**（parallelism）—— 同一时刻真的在跑，需要多核
- **进程**（process）—— 资源分配的单位，有自己的内存空间
- **线程**（thread）—— 操作系统调度的最小单位，同进程内共享内存
- **主线程**（main thread）—— JVM 启动时创建，执行 `main` 方法，名字就叫 `main`
- **`start()`** —— 创建新线程，由新线程去调 `run()`
- **`run()`** —— 线程的任务体；直接调它只是普通方法调用，跑在当前线程上
- **`Runnable`** —— 任务接口，把"干什么"和"谁来干"分开
- **`Callable`** —— 能返回结果、能抛异常的 `Runnable`
- **`FutureTask`** —— 包住 `Callable`，`get()` 拿结果
- **异步**（asynchronous）—— 发起和完成是两件事，发起方不等结果
- **`join()`** —— 阻塞**调用它的那个线程**，直到目标线程结束
- **线程生命周期**（lifecycle）—— `NEW` / `RUNNABLE` / `BLOCKED` / `WAITING` / `TIMED_WAITING` / `TERMINATED`
- **`RUNNABLE`** —— 正在跑或随时能跑，**Java 没有单独的 `RUNNING` 状态**
- **用户线程**（user thread）—— 默认类型，JVM 必须等它结束才退出
- **守护线程**（daemon thread）—— `setDaemon(true)`；用户线程一清零就被强制终止
- **中断**（interruption）—— 给线程设一个标志位，**停不停由线程自己决定**
- **中断标志**（interrupt status）—— `interrupt()` 置位，`isInterrupted()` 读，`interrupted()` 读并清
- **`InterruptedException`** —— 阻塞中的线程被中断时抛出，抛出时中断标志已被清除
- **吞掉中断**（swallowing the interrupt）—— `catch` 里什么都不做，信号丢失

## 九、下一课

这一课我们让线程跑起来了，但一直在回避一件事：**多个线程碰同一份数据会怎样？**

上面 2.1 提过，同一进程里的线程共享内存。那如果两个线程同时对
`count++` 呢？这一课所有例子里，共享的只有 `AtomicInteger` 和 `CountDownLatch`
这两个本来就线程安全的家伙——我是故意挑的。

下一课我们就把这个保护撤掉，看看 `count++` 在两个线程手里会少算多少，
再请出 `synchronized`。到时候 6.3 那个"循环里检查中断标志"的写法，
也会用得更放心——毕竟那时你才知道，为什么共享的变量不能随便读。

下期再见。
