上一课我们弄明白了"变量里装的是什么"。这一课讲**怎么让代码按你想要的方式走**——
判断往哪边走、循环转到什么时候停、什么时候该提前跳出。

这些东西每门语言都有，看起来没什么可讲的。但 Java 里有三处特别容易埋雷，
而且它们有个共同点：**编译器不会提醒你，只有跑起来才暴露**。

我们先来看第一处。

## 一、&& 的短路：右边的表达式可能根本没跑

先看一段你大概率写过的代码：

```java
String s = null;
if (s != null && s.length() > 0) {
    System.out.println("空字符串");
}
```

这行代码不会炸。为什么？因为 `s` 明明是 `null`，`s.length()` 按理说该抛 `NullPointerException`。

答案在 `&&` 的**短路**（short-circuit）语义上：**左边已经是 `false` 了，整个表达式不可能为真，
于是右边压根不去求值。** 右边那段代码像被"抄了近路"跳过去了，所以从来没执行到 `s.length()`。

这是 `&&` 和 `&` 最关键的区别。我们做个实验，让"右边到底跑没跑"变成看得见的事实——
给右边挂一个计数器：

```terminal
$ java src/main/java/dev/javalearning/basics/controlflow/ControlFlowDemo.java

========== 1. && 的短路：右边的表达式可能根本没跑 ==========
null != null && s.length() > 0  → false
右侧被跳过的调用次数            → 0
没有短路会怎样（结果先行）      → NullPointerException: Cannot invoke "String.length()" because "<local0>" is null

========== 2. || 的短路：找到真的就停下 ==========
true || 右边 → true

========== 3. switch 表达式：漏写分支编译器会说话 ==========
MAP  → 看地图
SOUTH → 向下

========== 4. 三种循环差在哪一步 ==========
while  先判断后执行，次数可能为 0
do-while 先执行后判断，至少跑 1 次
while 循环次数 = 0（条件一开始就是 false）
do-while 循环次数 = 1（同样从一开始就是 false）

========== 5. 增强 for 里删元素：有时炸有时不炸 ==========
删中间的元素「b」 → 没炸，结果 = [a, c]（删完刚好走完，纯属侥幸）
删第一个元素「a」 → ConcurrentModificationException
每个元素都删      → ConcurrentModificationException
迭代器自己的 remove → a,c
removeIf            → a,c

========== 6. break / continue / 标签 ==========
break 只能跳出一层：
  i=0 j=0
  i=1 j=0
  i=2 j=0
带标签的 break 直接跳出外层：
  i=0 j=0
（标签演示结束）
```

第三行是关键：把 `&&` 换成 `&`（单个与号），**两边都求值**，于是 `s.length()` 真的被调用了，
`NullPointerException` 当场抛出来。

| 运算符 | 语义 | 什么时候用 |
|---|---|---|
| `&&` | 左边 false 就停，**短路** | 判断条件，99% 的场景 |
| `&` | 两边都求值 | 位运算（`5 & 3`），或刻意需要两边副作用时 |

### 短路什么时候变成 bug

短路本身是好东西，但它藏着一条规则：**右边可能有副作用，而这些副作用不保证发生。**

```java
if (user != null && user.isActive() && logAccess(user)) {
    // ...
}
```

`logAccess(user)` 有副作用（写日志）。一旦前面某个条件不成立，它就不会被调用。
如果你的本意是"无论如何都要记一笔日志"，那这段代码就是错的——而且平时不报错，
只有某个用户恰好不是 active 时才悄悄漏记。这种 bug 极难查。

**规矩：条件表达式里只放"纯判断"的东西，别放有副作用的操作。** 想记账，单独写一行。

### `||` 同理，方向相反

`||` 的短路是**左边已经 `true` 就停**：

```java
if (name == null || name.isEmpty()) {   // name 是 null 时，右边不跑
    // ...
}
```

这一行能安全运行，靠的就是 `||` 的短路。

## 二、switch 表达式：让编译器替你检查漏没漏分支

老写法（switch 语句）有个著名陷阱——**漏写 `break` 会发生穿透**（fall through）：

```java
switch (level) {
    case 1:
        System.out.println("一");      // 忘了 break
    case 2:
        System.out.println("二");      // level=1 时这行也会执行
        break;
}
```

`level` 是 1，结果是"一"和"二"都打印。这是新手最常踩的坑之一，而编译器一声不吭。

Java 14 之后有了 **switch 表达式**，用箭头语法，**默认就没有穿透**：

```java
String text = switch (level) {
    case 1 -> "一";
    case 2 -> "二";
    default -> "未知";
};
```

更重要的是：**switch 表达式要求穷尽所有情况，漏一个编译器直接报错。**

我把这个错误真实跑了出来，写在 [`MissingCase.java`](../src/main/java/dev/javalearning/basics/controlflow/broken/MissingCase.java)
里——它放在 `broken/` 包里，是故意写错的，已经被排除出 Gradle 构建，IDE 里标红是正常的：

```terminal
$ javac -encoding UTF-8 -d out src/main/java/dev/javalearning/basics/controlflow/broken/MissingCase.java
src/main/java/dev/javalearning/basics/controlflow/broken/MissingCase.java:16: error: the switch expression does not cover all possible input values
        return switch (d) {
               ^
1 error
```

`the switch expression does not cover all possible input values`——
**没有覆盖所有可能的输入值**。注意这是在**编译期**就报错，不是运行期。
以后你往枚举里加一个新值，所有漏写它的 switch 会集体变红，你想漏都漏不掉。

这正是该用 switch 表达式而不是 if-else 链的理由：**它把一类运行时错误提前到了编译期。**

### 什么时候可以省掉 default

如果 switch 的是**枚举类型**，而且你列全了所有枚举值，那 `default` 可以不写——
编译器知道已经穷尽了。但有两种情况必须写：

- switch 的是 `int`、`String` 这类取值范围开放的类型
- 你故意想兜住"意料之外的值"

防御性编程的共识是：**宁可写一个 `default -> throw`，也不要留一个静默的空分支。**

## 三、三种循环差在哪一步

`for`、`while`、`do-while` 三兄弟，功能上几乎一样，区别只在**判断的时机**：

| 循环 | 判断时机 | 最少执行次数 |
|---|---|---|
| `while` | 先判断，后执行 | 0 次 |
| `do-while` | 先执行，后判断 | **1 次** |
| `for` | 先判断，后执行（计数器自带） | 0 次 |

我们用真跑出来的数字记住这件事。条件是 `i < 0`，一开始就不成立：

```terminal
========== 4. 三种循环差在哪一步 ==========
while 循环次数 = 0（条件一开始就是 false）
do-while 循环次数 = 1（同样从一开始就是 false）
```

**同样的条件，`while` 跑了 0 次，`do-while` 跑了 1 次。**

```java
while (i < 0) { i++; }        // 0 次

do { i++; } while (i < 0);    // 1 次——先干再说
```

那 `do-while` 到底什么时候用？一个典型场景是"**先做一次，再问要不要继续**"：

```java
String input;
do {
    input = scanner.nextLine();
    process(input);
} while (!input.equals("quit"));
```

必须至少处理一次用户输入，所以判断放后面。除这种场景外，日常几乎都用 `while` 和 `for`。

### for 的三段式

```java
for (int i = 0; i < 10; i++) { ... }
//    ①初始化   ②条件   ③步进
```

三段各自的生命周期不一样：**①只跑一次，②每轮都跑，③每轮末尾跑。**
知道这个就能解释一个常见疑惑——`for` 里声明的变量在循环外不能访问，因为它活在①~③这个范围里。

## 四、增强 for 里删元素：有时炸，有时不炸

这一节是这一课最值钱的部分，因为它**看起来毫无道理**。

先看结论，三种写法：

```terminal
========== 5. 增强 for 里删元素：有时炸有时不炸 ==========
删中间的元素「b」 → 没炸，结果 = [a, c]（删完刚好走完，纯属侥幸）
删第一个元素「a」 → ConcurrentModificationException
每个元素都删      → ConcurrentModificationException
迭代器自己的 remove → a,c
removeIf            → a,c
```

来，我们逐个看。同样是在 for-each 循环里调 `list.remove(...)`：

- **删中间的元素「b」——没炸**
- **删第一个元素「a」——炸了**
- **每个元素都删——炸了**

凭什么？删中间反倒安全，删第一个就不行？

### modCount：一个你看不见的计数器

`ArrayList` 内部有个字段叫 `modCount`，**记录这个列表被结构性修改过几次**
（add、remove 都算，改元素内容不算）。

for-each 循环底层是迭代器在工作，而迭代器会记住"我创建的时候，`modCount` 是多少"。
每次调 `next()` 取下一个元素时，它都会对一遍账：

> 我创建时 modCount = 0，现在是多少？
> 如果变了，说明有人绕开我改过列表——那我拒绝继续，抛 `ConcurrentModificationException`。

现在三种情况全解释通了：

| 情况 | 删完之后 | 下一次 next()？ | 结果 |
|---|---|---|---|
| 删「b」 | modCount 变了，但**刚好没有下一次 next()** 了 | 没有 | 无人生还……啊不，无人检查，侥幸没炸 |
| 删「a」 | modCount 变了，后面还有「b」「c」要走 | 有 | 对账失败，抛异常 |
| 每个都删 | 每次删完后面都还有 next() | 有 | 抛异常 |

**所以删「b」没炸，不是因为"删中间安全"，而是纯粹走运。**
列表走到 `b` 时，删掉它，然后迭代器发现已经到尾部了，循环自然结束——
`modCount` 的变化从头到尾没被检查过。

### 正确的两种写法

**写法一：用迭代器自己的 `remove`。** 迭代器知道自己删的，删完会同步更新自己的记录：

```java
for (Iterator<String> it = list.iterator(); it.hasNext(); ) {
    if (it.next().equals("b")) {
        it.remove();        // ← 注意是 it.remove()，不是 list.remove()
    }
}
```

**写法二：`removeIf`，一行搞定。** 这是日常推荐：

```java
list.removeIf(s -> s.equals("b"));   // 结果 a,c
```

`removeIf` 的参数是个 Lambda，[Lambda 表达式](./07-Lambda表达式.md)那一课会专门讲。现在先记住这个形状就行。

**一句话总结：不要在 for-each 里调集合自己的 remove，要用 `it.remove()` 或者 `removeIf`。**
这不是代码风格问题，是"有时炸有时不炸"的随机 bug 问题。

## 五、break / continue / 标签

`break` 跳出循环，`continue` 跳过这次迭代，都知道。容易忘的是：**`break` 只能跳出一层。**

```java
for (int i = 0; i < 3; i++) {       // 外层
    for (int j = 0; j < 3; j++) {   // 内层
        if (j == 1) break;          // 只打破内层
    }
}
// 外层还是会跑完 0、1、2 三轮
```

想一次跳两层，用**标签**（label）——一个标识符加冒号，贴在循环头上：

```java
outer:
for (int i = 0; i < 3; i++) {
    for (int j = 0; j < 3; j++) {
        if (j == 1) break outer;   // 两层一起跳出去
    }
}
// 外层只跑了 1 轮就结束了
```

我们把这俩的区别跑成了数字：

```terminal
========== 6. break / continue / 标签 ==========
break 只能跳出一层：
  i=0 j=0
  i=1 j=0
  i=2 j=0
带标签的 break 直接跳出外层：
  i=0 j=0
（标签演示结束）
```

断言里钉得很直接：不带标签外层跑 **3** 轮，带标签外层只跑 **1** 轮。

`continue` 也一样，只跳过当前这一轮，循环本身还在转。测试里的 `continueSum()`
算的是 1 到 5 的奇数和——跳过了 2 和 4，结果还是 `1 + 3 + 5 = 9`。

**说句实话：标签在实际项目里很少见**，多数人能绕开它（把内层循环抽成一个方法，
`return` 就是跳出两层）。但看得懂是必要的，维护老代码时会遇到。

## 六、不推荐的用法

- **别在条件表达式里放有副作用的操作**（写日志、改状态）。短路会让它不确定执行
- **别用 `&` / `|` 做逻辑判断**，那是位运算。想短路就 `&&` / `||`
- **别漏写 `break`**，或者干脆改用 switch 表达式——它默认就不穿透
- **别在 for-each 里调集合自己的 `remove`**，用 `it.remove()` 或 `removeIf`
- **别用标签当常规武器**。真需要跳出多层时，优先把内层抽成方法
- **别写 `while (true)` 然后靠里面的 `break` 溜出来**——条件写清在哪，比在函数中部跳出来好读

## 七、这一课的术语表

- **短路求值**（short-circuit evaluation）—— `&&` 左边 false 就停，`||` 左边 true 就停
- **副作用**（side effect）—— 表达式除了返回值之外还改了别的东西
- **fall through**（穿透）—— switch 漏写 break，顺着下一个 case 继续跑
- **switch 表达式**（switch expression）—— Java 14+，用 `->`，默认不穿透，且必须穷尽
- **穷尽性**（exhaustiveness）—— switch 表达式必须覆盖所有可能的输入，否则编译报错
- **`modCount`** —— `ArrayList` 内部记录结构性修改次数的计数器
- **fail-fast**（快速失败）—— 发现列表被绕开自己改过，立刻抛异常而不是继续跑
- **迭代器**（iterator）—— for-each 底层靠它工作，有自己的 `remove`
- **`removeIf`** —— 按条件批量删除，一行搞定
- **`do-while`** —— 先执行后判断，至少跑一次
- **标签**（label）—— `outer:` 这样的记号，配合 `break outer` 跳出指定层

## 八、下期再见

我们来总结一下。这一课讲了四件事，但它们的共同点只有一个：

> **编译器不会提醒你的错误，才是真的会咬人的错误。**

短路让副作用不确定执行；`&&` 写成 `&` 从"安全"变成"NPE"；switch 漏写分支老写法静默穿透、
新写法直接编译不过；for-each 里删元素有时炸有时不炸——**四种坑，编译器全都放过你**。

所以要记住的不是规则本身，而是这个判断标准：**当编译器不说话时，你要多留一分心。**
也是因为这个，这一课的代码全都跑过、断言全都钉住了——我写"删中间不炸"的时候，
一开始也以为是"删中间安全"，跑完才发现是侥幸。我把自己搞错的过程留在了断言里。

下一课我们讲**方法**：为什么要抽方法、参数传进去到底发生了什么、
为什么方法里改了参数外面的变量没反应——那个问题的答案会彻底改变你对 Java 的理解。
