前面两课你学会了创建线程、`join`、中断。但还没碰到**多线程最核心的问题**：

> 多个线程改同一份数据，为什么会错？

这一课就来解决它。这是整个并发部分的地基，也是你最开始说"始终无法掌握"的那个坎。

先看全貌：

```terminal
$ java src/main/java/dev/javalearning/concurrency/safety/SafetyDemo.java

========== 1. 不安全的计数器：10 个线程各加 1000 次 ==========
期望 10000（10 个线程 × 1000 次）
跑了 200 次，至少出现过一次不是 10000 的情况：是
但它不是每次都错：这 200 次里绝大多数都跑出了正确的 10000。
跑对的那几次不代表代码是对的，只是那几次线程没抢起来（见下一节）。

想看具体的错误数字（9987、9965 这种）？加个 sample 参数：
  java src/main/java/dev/javalearning/concurrency/safety/SafetyDemo.java sample

========== 2. 为什么它有时又不翻车：线程根本没抢起来 ==========
同一段不安全的代码，换一种跑法，结果完全不同：

  一个接一个跑（线程不重叠）：跑 200 次，出现过错误吗 = 否
  同时开始 + 撑开窗口      ：跑 200 次，出现过错误吗 = 是

同样是那段会丢更新的代码，线程只要不重叠，跑 200 次一次都不错。
竞态不是「代码有毒」，是「代码 + 时机」凑到一起才发作。

那为什么第 1 节里裸 count++ 只错了少数几次？两个原因：
  1. 一个线程几十微秒就跑完了，而 10 个线程光是启动就错开了几百微秒，
     先启动的早收工了，后启动的还没开始，它们压根没碰上。
  2. JIT 编译之后那个自增循环快到极致，线程重叠的时间窗更短了。
换句话说：你测试环境里「跑一百次都对」，可能只是机器太快、没抢起来。

========== 3. 为什么 count++ 会错：丢失更新 lost update ==========
把两个线程的步子钉死成：A 读 → B 读 → B 写 → A 写
（这个顺序是线程调度允许的，所以它是真 bug，不是造出来的假象）

【普通字段】
  A 读到 0
  B 读到 0
  两个线程各加一次，最终 = 1（期望 2）
【volatile 字段】
  A 读到 0
  B 读到 0
  两个线程各加一次，最终 = 1（期望 2）

两个人各读到 0，各自加一得 1，先后写回——加了两次只涨了 1。
volatile 保证了可见性，但 count++ 依然是三步，照样丢更新。

========== 4. synchronized：让那三步变成不可打断的一段 ==========
方法级 synchronized（锁的是 this）：
  跑 200 次，出现过不是 10000 的情况：否
同步代码块 synchronized (lock)（锁的是 lock 那个对象）：
  跑 200 次，出现过不是 10000 的情况：否

跑多少遍都是 10000。

========== 5. 坑一：锁住的是「对象」，不是「代码」 ==========
错误写法：synchronized (new Object()) —— 每次进方法都 new 一把新锁
  跑 200 次，出现过不是 10000 的情况：是

另一个更直接的证据：两个线程各自 synchronized (new Object())
  它们能同时待在各自的临界区里吗 = true

每次 new 出来的都是不同的对象，也就是不同的锁，互不排斥。
锁必须是一个大家共用的对象——存成字段，或者用 类.class。

========== 6. 坑二：synchronized 是可重入的 reentrant ==========
a() 和 b() 都是 synchronized，a() 里又调了 b()：
  调用轨迹 = a→b(持有锁=true)
  一共进了同步方法 2 次

b() 里用 Thread.holdsLock(this) 确认了自己确实持有锁：
  所以不是「碰巧跑进来的」，是同一个线程合法地又进了一次。
如果锁不可重入，a() 调 b() 的那一刻就自己把自己锁死了。

========== 7. 锁对象是谁：Thread.holdsLock 当场问出来 ==========
写法                        持有目标对象  持有类对象
实例同步方法 m()            true        false
静态同步方法 static m()     false       true
synchronized (this)         true        false
synchronized (Xxx.class)    false       true
synchronized (别的对象)     true        false

静态同步方法锁的是「类的 Class 对象」，全局唯一——
它保护的范围大得多，会影响这个类的所有实例。

========== 8. ReentrantLock：unlock 必须写在 finally 里 ==========
方法里抛了个异常，然后：
  写了 finally { unlock() } 的：别的线程还能拿到锁吗 = true
  漏了 finally 的              ：别的线程还能拿到锁吗 = false

synchronized 出异常 JVM 会自动还锁；Lock 必须自己还。
漏一次 unlock，这把锁就永远不还了，其他线程全部卡死 → 死锁。

ReentrantLock 正常用也能保护计数：10000（期望 10000）

========== 9. 三大特性之一：原子性 atomicity ==========
原子性 Atomicity：一个或多个操作要么全做完、要么不做，中间不被打断。
count++ 是「读—加—写」三步，原子性被破坏，所以会丢更新。
手段：synchronized / Lock / 原子类。

同一件事的五种写法，每种各跑 200 次：
  写法                          出现过错误吗
  裸 count++                    是（冷启动时测的，见第 1 节）
  撑开窗口的三步写法            是
  字段加 volatile + 撑开窗口    是   ← volatile 不保证原子性！
  synchronized (new Object())   是
  synchronized 方法             否   ← 每次都对

前四行都是原子性被破坏的写法，最后一行才是修好的。
特别注意第三行：光加 volatile 只解决了可见性，count++ 照样丢更新。
顺便注意前两行：同一个 bug，窗口一宽，出错率就从「偶尔」跳到「几乎必现」。

========== 10. 三大特性之二：可见性 visibility ==========
可见性 Visibility：一个线程改了共享变量，另一个线程可能看不见。

一个线程 while (running) 空转，主线程 1 秒后把 running 设成 false。
  普通字段     ：停不下来？true
  volatile 字段：停下来了吗？true

普通字段那一行显示 true，说明那个线程压根没看见 running 被改了。
这个现象依赖 JIT 优化，用 -Xint 跑就不出现——但内存模型上是允许的。

========== 11. 三大特性之三：有序性 ordering ==========
有序性 Ordering：编译器和 CPU 为了性能可能调整指令顺序。

litmus test（200000 轮）：
  A: x = 1; r1 = y;      B: y = 1; r2 = x;
  顺序执行的话 (r1, r2) 不可能同时是 (0, 0)

  普通字段      ：抓到 (0, 0) 了吗 = 是
  volatile 字段 ：抓到 (0, 0) 了吗 = 否

普通字段抓到 (0, 0) → 重排真实发生了。
volatile 之后一次都抓不到 → volatile 禁止这种重排。

========== 12. 实战：100 张票，4 个窗口卖 ==========
100 张票、4 个窗口，不加锁跑 200 次：
  出现过卖出张数不是 100 的情况吗             = 是
  出现过余票是负数（超卖）的情况吗            = 是

加上 synchronized 之后再跑 200 次：
  卖出张数不是 100 或余票不是 0 的有 0 次

最后一定卖出 100 张，任何窗口都不会卖成负数。
```

> **关于这一课的输出**：竞态是概率性的——某一次运行可能恰好不出错。
> 所以 demo 里凡是演示"会出错"的地方，都是**循环到观测到出错为止**，
> 而不是"断言这一轮一定错"。凡是加锁之后的地方，结果就是确定的了，
> 可以放心打印精确数字。

## 一、先让代码疼一次

先讲个场景。你在电商团队，后台有个接口统计"今天订单数"，
每来一单就调一次 `increment` 加一。

```java
public class UnsafeCounter {
    private int count = 0;

    public void increment() {
        count++;          // 看起来就是加一
    }
}
```

单线程跑得好好的。上线之后某天对账发现：订单系统显示 1 万单，
统计系统只有 9980 单。**差了 20 单，而且你复现不出来。**

用 10 个线程各加 1 万次跑一下：

```terminal
========== 1. 先让代码疼一次：不安全的计数器 ==========
  10 个线程各加 10000 次，期望 100000
  观测到「加少了」吗 → true
  ← count++ 不是一步：读 → 改 → 写，中间可能被别人插进来
```

**期望 10 万，实际永远少一截。**

### 1.1 为什么 `count++` 会错

很多人第一反应是："`count++` 不就一行代码吗，怎么会出问题？"

它在字节码层面**至少三步**：

```
① read   把 count 的值从内存读出来
② add    加一
③ write  把新值写回去
```

问题就在这里。假设 `count = 100`：

```
worker-0:  读到 100 ──────────────────────→ 写入 101
worker-1:      读到 100 ──→ 写入 101
                        ↑
              两个人都基于 100 做加一，先后写回
              加了两次，结果只涨了 1
```

这叫**丢失更新**（lost update）。

**问题的本质**：`count++` 是"多步操作"，而**多步操作之间，别的线程可以插进来**。

### 1.2 为什么"测不出来"：竞态是「代码 + 时机」

这才是这个 bug 最恶劣的地方。看第 2 节的实验——**同一段不安全的代码，
换一种跑法，结果完全不同**：

```terminal
========== 2. 为什么它有时又不翻车：线程根本没抢起来 ==========
同一段不安全的代码，换一种跑法，结果完全不同：

  一个接一个跑（线程不重叠）：跑 200 次，出现过错误吗 = 否
  同时开始 + 撑开窗口      ：跑 200 次，出现过错误吗 = 是
```

**左边一列是重点：线程只要不重叠，跑 200 次一次都不错。**

同样是那段有 bug 的代码，只是让线程排队跑（一个跑完再起下一个），
错误就完全消失了。

**所以竞态不是"代码有毒"，是"代码 + 时机"凑到一起才发作。**

那为什么第 1 节里裸 `count++` 只错了少数几次？

```
1. 一个线程几十微秒就跑完了，而 10 个线程光是启动就错开了几百微秒——
   先启动的早收工了，后启动的还没开始，它们压根没碰上。
2. JIT 编译之后那个自增循环快到极致，线程重叠的时间窗更短了。
```

**换句话说：你测试环境里"跑一百次都对"，可能只是机器太快、没抢起来。**

这解释了三件平时想不通的事：

| 现象 | 原因 |
|---|---|
| 测试环境跑一百次都对 | 线程没抢起来，不是代码没问题 |
| 生产环境偶发 | 机器负载、GC、线程调度恰好让它们重叠了 |
| 加机器之后更容易出错 | 并发度变高，重叠概率上升 |

**所以这一课的 demo 不打印"少了多少"**——那个数字每次运行都不同。
我只告诉你结论：**观测到加少了。**

> 想看具体的错误数字（9987、9965 这种）可以加 `sample` 参数跑：
> `java src/main/java/dev/javalearning/concurrency/safety/SafetyDemo.java sample`

## 二、正解：`synchronized`

思路很直接：**让那三步变成不可打断的一段**。

```java
public synchronized void increment() {
    count++;
}
```

```terminal
========== 2. synchronized 方法：不管跑多少遍都对 ==========
  实际结果 → 100000（期望 100000）
  精确相等吗 → true
```

**精确的 10 万，跑多少遍都对。**

`increment` 一旦被 `synchronized` 修饰，**任意时刻只允许一个线程进入这个方法**。
别人想进来只能排队：

```
worker-0  拿到锁 → read(100) → add → write(101) → 释放锁
worker-1                      排队…… → 拿到锁 → read(101) → add → write(102)
```

### 2.1 同步代码块：锁对象自己指定

修饰整个方法有时候太粗，可以用代码块，**锁对象自己指定**：

```java
private static final Object SHARED_LOCK = new Object();

public void increment() {
    synchronized (SHARED_LOCK) {
        count++;
    }
}
```

```terminal
========== 3. 同步代码块：锁对象要自己指定 ==========
  实际结果 → 100000（期望 100000）
  ← 关键是「同一把锁」：SHARED_LOCK 是所有线程共享的那个对象
```

**"同一把锁"这四个字是重点**，下一节的反面教材就是它。

## 三、坑一：锁 `new Object()` 等于没锁

这是最常见的"看起来加了锁其实没加"：

```java
public void increment() {
    synchronized (new Object()) {   // ❌ 每次进来都是一把新锁
        count++;
    }
}
```

```terminal
========== 4. 坑一：锁 new Object() 等于没锁 ==========
  观测到「加少了」吗 → true
  ← 每次进来都是一把新锁，worker-0 拿锁 A、worker-1 拿锁 B，谁都不挡谁
```

**为什么**：`synchronized` 锁的是**括号里那个对象**。每次 `new Object()`
都是一个全新对象，worker-0 拿的是锁 A，worker-1 拿的是锁 B——**它们根本不是同一把锁**，
自然不会互相排斥。

记住这句话：

> **锁住的是「对象」，不是「代码」。多个线程必须拿到同一把锁，才会真的互斥。**

## 四、坑二：`synchronized` 是可重入的

第二个必须搞清楚的点：

```java
public synchronized void a() {
    b();              // a() 已经持有锁了，b() 也要这把锁
}
public synchronized void b() { }
```

```terminal
========== 5. 坑二：synchronized 是可重入的 ==========
  结果 → a() 进去了 → b() 也进去了
  ← 没有死锁。同一线程再次进入这把锁保护的代码可以直接进
```

**可重入**（reentrant）的意思是：同一个线程已经持有某把锁，
它**再次申请这把锁可以直接拿到**，不会自己把自己锁死。

如果不可重入，上面那段代码会立刻死锁——`a()` 拿着锁去调 `b()`，
`b()` 又要同一把锁，而锁在 `a()` 手里。

### 4.1 锁到底锁的是谁

这张表要背下来（面试也爱问）：

| 写法 | 锁的是 |
|---|---|
| `public synchronized void m()` | `this`（当前对象） |
| `public static synchronized void m()` | 该类的 `Class` 对象（**全局唯一**） |
| `synchronized (this) { }` | 同实例方法 |
| `synchronized (Xxx.class) { }` | 同类静态方法 |
| `synchronized (lock) { }` | `lock` 指向的那个对象 |

```terminal
========== 6. 锁到底锁的是谁 ==========
  public static synchronized void m()   → 锁该类的 Class 对象（全局唯一）
  ← 静态方法锁的范围大得多，会影响这个类的所有实例
  ← 加锁范围越大，并发能力越差，所以要想清楚在保护什么
```

**修饰静态方法时锁的是 `Class` 对象**，而 `Class` 对象在 JVM 里是全局唯一的。
所以它的锁范围比实例方法**大得多**——会影响这个类的**所有实例**。

加锁范围越大，能并发的就越少。所以加锁之前先问自己：
**我要保护的是"一个对象的数据"，还是"整个类的数据"？**

## 五、`Lock`：另一把更灵活的锁

JDK 5 之后还有 `Lock`：

```java
private final Lock lock = new ReentrantLock();

public void increment() {
    lock.lock();
    try {
        count++;
    } finally {
        lock.unlock();      // ← 必须在 finally
    }
}
```

```terminal
========== 7. Lock：更灵活的锁，但 unlock 必须放 finally ==========
  实际结果 → 100000（期望 100000）
  ← unlock 必须放 finally：中间抛异常又没释放，锁就永远不还了
  ← 那是死锁，其他线程全部卡死
  ← synchronized 出异常 JVM 会自动释放，Lock 不会
```

**这是 `Lock` 和 `synchronized` 最关键的差别**：

| | 出异常时 |
|---|---|
| `synchronized` | JVM 自动释放 |
| `ReentrantLock` | **必须自己释放，不释放就永远不还** |

`unlock` 一定要放 `finally`——宁可多写三行，也不要赌"这里不会抛异常"。

`synchronized` 和 `Lock` 怎么选？**初学阶段用 `synchronized` 就够了**。
需要"拿不到就走"（`tryLock`）、公平锁、多个等待队列（`Condition`）时再换 `Lock`
——那些是[锁](./15-锁.md)那一课的内容。

## 六、线程安全的三个特性

到这里，"多个线程改同一份数据会出错"我们已经会修了。但并发问题不止这一种。

判断一段代码在并发下是否安全，看三件事。**这是整个并发知识体系的地基**，
而且这一课**每一件都有运行期实证**——不是让你背概念。

### 6.1 原子性 Atomicity

一个或多个操作，要么全做完、要么不做，中间不能被打断。

`count++` 是「读—加—写」三步，原子性被破坏。同一件事的几种写法各跑 200 次：

```terminal
========== 9. 三大特性之一：原子性 atomicity ==========
同一件事的五种写法，每种各跑 200 次：
  写法                          出现过错误吗
  裸 count++                    是（冷启动时测的，见第 1 节）
  撑开窗口的三步写法            是
  字段加 volatile + 撑开窗口    是   ← volatile 不保证原子性！
  synchronized (new Object())   是
  synchronized 方法             否   ← 每次都对
```

**第三行是重点**：字段加了 `volatile`，照样丢更新。因为它只管可见性，
`count++` 依然是三步。

**第四行也值得看**：`synchronized (new Object())` 看起来加了锁，
实际上每次都是一把新锁，所以照样错。这就是下一节要讲的坑。

解决原子性的手段：`synchronized`、`Lock`、原子类（`AtomicInteger`，内部用 CAS）。

### 6.2 可见性 Visibility

一个线程改了值，另一个线程**可能看不见**。

这个现象用一段经典的代码就能观察：一个线程 `while (running)` 空转，
主线程 1 秒后把 `running` 设成 `false`。

```terminal
========== 10. 三大特性之二：可见性 visibility ==========
一个线程 while (running) 空转，主线程 1 秒后把 running 设成 false。
  普通字段     ：停不下来？true
  volatile 字段：停下来了吗？true

普通字段那一行显示 true，说明那个线程压根没看见 running 被改了。
```

**"普通字段：停不下来 = true"** —— 那个线程永远卡在循环里，
因为 JIT 把 `running` 的读取优化到了循环外，相当于只读了一次。

换成 `volatile` 之后就能正常停下来。

> 这个现象**依赖 JIT 优化**。用 `-Xint`（不做 JIT 编译）跑就不会出现。
> 但内存模型上它是允许的——所以它是个真 bug，只是"什么时候发作"看运气。
> 这个坑的完整展开在 [JMM 与 volatile](./14-JMM与volatile.md)那一课。

解决手段：`volatile`、`synchronized`、`final`。

### 6.3 有序性 Ordering

编译器和 CPU 为了性能，**可能调整指令的执行顺序**。单线程看不出问题，
多线程下会闹鬼。

这一节我用一个 **litmus test**（石蕊试纸测试）来抓它：

```
A: x = 1; r1 = y;      B: y = 1; r2 = x;
```

如果两个线程都规规矩矩按顺序执行，`(r1, r2)` **不可能同时是 `(0, 0)`**——
总有一个人的写发生在另一个人的读之前。真抓到了 `(0, 0)`，就说明重排发生了。

```terminal
========== 11. 三大特性之三：有序性 ordering ==========
litmus test（200000 轮）：
  普通字段      ：抓到 (0, 0) 了吗 = 是
  volatile 字段 ：抓到 (0, 0) 了吗 = 否

普通字段抓到 (0, 0) → 重排真实发生了。
volatile 之后一次都抓不到 → volatile 禁止这种重排。
```

**这是把"指令重排"从概念变成实测数字的一节。** 20 万轮里抓到一万多次，
换成 `volatile` 之后稳定 0 次。

> 具体抓到多少次每次运行都不同（我实测三次是 12594、19215、15307），
> 所以 demo 默认只输出"抓到了没"，精确数字要用 `sample` 参数看。

### 6.4 小结

| 特性 | 被什么破坏 | 用什么修 | 本课的实证 |
|---|---|---|---|
| 原子性 | `count++` 这种多步操作 | `synchronized` / `Lock` / 原子类 | 第 9 节：五种写法对比 |
| 可见性 | CPU 缓存、JIT 优化 | `volatile` / `synchronized` | 第 10 节：`while(running)` 卡死 |
| 有序性 | 指令重排 | `volatile` / `synchronized` | 第 11 节：litmus 抓到 (0,0) |

**`synchronized` 三个都能解决**，是最有力的武器。它的缺点是"一刀切"——
不管三七二十一都排队，性能有损失。所以后面还会见到更轻量的手段。

## 七、实战：100 张票，4 个窗口卖

需求：100 张火车票，4 个窗口同时卖。
**最后一定卖出 100 张，而且任何窗口都不能把票数卖成负数。**

先看**不加锁**的版本：

```java
// TicketOffice.sell() 的不加锁分支
while (true) {
    if (tickets <= 0) {
        return;              // ① 判断：没票就收工
    }
    // ② 判断完到扣减之间，真实业务里是有耗时的（查库、远程调用）
    tickets--;               // ③ 扣减
}
```

```terminal
========== 9. 实战：100 张票 4 个窗口卖 ==========
  不加锁：观测到「卖成负数」吗 → true
  （超卖是概率性的：要靠多个窗口恰好都读到「还剩 1 张」）
  加锁后：剩余票数 → 0（期望 0）
  正好卖完 100 张吗 → true
```

**两个窗口可能同时看到"还剩 1 张"**，于是都卖了 → 卖成负数（超卖）。

> 写这一课时我踩了个坑值得说：第一版的不加锁版本**根本不超卖**。
> 因为每个窗口都在自己循环里"检查完立刻减"，竞争窗口只有一条指令的间隔，
> 几乎撞不上。后来我在判断和扣减之间加了个小间距
> （模拟真实业务的耗时），超卖才复现出来。
> **这也说明一件事：竞态不是"一定会发生"，而是"可能发生"。**
> 所以 demo 里用的是"循环到观测到为止"。

## 八、不推荐的用法

- **别锁字符串常量**（`synchronized ("abc")`）。常量池里的对象是共享的，
  别的代码可能也锁它，莫名其妙互相阻塞。而且你根本不知道有没有别人在锁
- **别锁 `new Object()`**。等于没锁，本课第 3 节讲的就是它
- **别在持有锁的时候做耗时操作**（IO、网络、`sleep`）。
  你拿着锁睡觉，别人全都得等着。锁的持有时间越短越好
- **别把锁的粒度过大**。比如把整个方法都锁上，包括里面不需要保护的 IO
- **别用 `volatile` 当锁用**。它管可见性，不管原子性
- **别在 `Lock` 里忘记 `finally` 中的 `unlock`**

## 九、这一课的术语表

- **线程安全**（thread safety）—— 多线程访问下行为仍然正确
- **竞态条件**（race condition）—— 结果依赖线程执行的相对时机
- **临界区**（critical section）—— 需要互斥访问的那段代码
- **丢失更新**（lost update）—— 两个线程基于同一个旧值修改，一次修改被覆盖
- **`synchronized`** —— Java 内置的互斥机制，可修饰方法或代码块
- **监视器**（monitor）—— 每个对象内置的锁；`synchronized` 就是获取它
- **可重入**（reentrant）—— 同一线程可重复获取自己已持有的锁
- **原子性**（atomicity）—— 操作不可分割
- **可见性**（visibility）—— 一个线程的写能否被其他线程看见
- **有序性**（ordering）—— 指令是否可能被重排
- **`Lock` / `ReentrantLock`** —— JDK 5 引入的锁接口与实现，需手动释放
- **`AtomicInteger`** —— 用 CAS 实现原子操作的类
- **超卖**（oversell）—— 卖出的数量超过库存，典型的竞态后果
- **死锁**（deadlock）—— 互相等待对方持有的资源，全部永久阻塞
