前面几课我们一直在 `new Thread()`。这一课要说清楚：
**为什么生产代码里几乎不会直接 `new Thread()`。**

先看全貌：

```terminal
$ java src/main/java/dev/javalearning/concurrency/pool/PoolDemo.java

========== 1. 为什么不直接用 new Thread ==========
  两种做法各跑 2000 个空任务
  池子明显更快吗 → true
  ← 池子复用了线程，省掉了反复创建/销毁的开销
  ← 这里不打印具体毫秒数：同一份代码跑十次能差一倍，贴出来会误导

========== 2. 七个参数，和真实的执行顺序 ==========
  提交任务1 成功  (线程数=1, 队列=0)
  提交任务2 成功  (线程数=1, 队列=1)
  提交任务3 成功  (线程数=1, 队列=2)
  提交任务4 成功  (线程数=2, 队列=2)
  提交任务5 被拒绝  (线程数=2, 队列=2)
  提交任务6 被拒绝  (线程数=2, 队列=2)
  ← 顺序是：先占满核心线程 → 再进队列 → 队列满了才加到最大线程 → 再满就拒绝

========== 3. 队列满了之后的四种拒绝策略 ==========
  AbortPolicy（默认）       → 抛 RejectedExecutionException
  CallerRunsPolicy          → 提交任务的线程自己跑（变相降速）
  DiscardPolicy             → 静默丢掉
  DiscardOldestPolicy       → 丢掉队列里最老的那个，再试一次
  第三个任务由谁执行 → main（提交它的线程是 main）
  ← CallerRunsPolicy 让调用方自己跑，等于给上游一个背压信号

========== 4. 为什么阿里手册不让用 Executors ==========
  newFixedThreadPool(2)
    队列 → LinkedBlockingQueue，剩余容量 = 2147483647  ← 无界！
    最大线程数 = 2
  newCachedThreadPool()
    队列 → SynchronousQueue，剩余容量 = 0
    最大线程数 = 2147483647  ← 无界！
  newScheduledThreadPool(2)
    队列 → DelayedWorkQueue，剩余容量 = 2147483647  ← 无界！
    最大线程数 = 2147483647  ← 无界！
  newSingleThreadExecutor() 的实际类型 → AutoShutdownDelegatedExecutorService
    不能强转成 ThreadPoolExecutor（它是包装过的）
  newWorkStealingPool() 的实际类型 → ForkJoinPool（另一套实现，不是 ThreadPoolExecutor）
  ← 结论：这几个快捷方法要么队列无界、要么线程无界，都可能 OOM
  ← 生产上应该手动 new ThreadPoolExecutor，把七个参数写清楚

========== 5. execute vs submit：一个吞异常，一个能拿到 ==========
  未捕获异常处理器收到 → execute-demo 抛了 IllegalStateException: execute 里抛的
  execute 提交的任务抛异常 → 主线程完全收不到（只有未捕获处理器知道）
  submit 提交的任务抛异常  → 不调 get() 的话同样看不到
  调 future.get() 之后    → 抛 ExecutionException，原因是 IllegalStateException: submit 里抛的
  submit 的返回值         → 42

========== 6. 优雅停机：shutdown vs shutdownNow ==========
  shutdown() 之后 isShutdown = true
  等它跑完 → 完成了 3 个，terminated = true
  shutdownNow() 返回了 4 个没来得及跑的任务
  ← 注意：它只是「尝试」中断，不响应中断的任务照样跑完

========== 7. 线程工厂：给线程起名字 ==========
  任务跑在 → order-pool-1
  任务跑在 → order-pool-2
  任务跑在 → order-pool-3
  ← 线程名带业务含义，jstack 里一眼能认出是哪个池
```

## 一、先让代码疼一次

最直觉的写法是"一个任务一个线程"：

```java
for (Task task : tasks) {
    new Thread(task::run).start();
}
```

2000 个任务就是 2000 个线程。问题有三个：

1. **创建和销毁都要花钱**。操作系统线程不是免费的，频繁创建销毁开销很大
2. **数量不受控**。1 万个任务就是 1 万个线程，每个线程还要占栈内存
   （默认 1MB 左右），直接 OOM
3. **没法管理**。想限制并发数、想排队、想监控，都没地方下手

第 1 节的实验就是对比这一点：

```terminal
========== 1. 为什么不直接用 new Thread ==========
  两种做法各跑 2000 个空任务
  池子明显更快吗 → true
  ← 池子复用了线程，省掉了反复创建/销毁的开销
  ← 这里不打印具体毫秒数：同一份代码跑十次能差一倍，贴出来会误导
```

> **关于最后那行说明**：这一节是性能测量，我实测同一份代码跑十次能差一倍，
> 所以 demo 里**故意不打印具体毫秒数**——贴出来会误导人以为那是稳定结论。
> 你能确认的是方向：池子明显更快。

**线程池的核心思想**：线程**复用**。池子里养几个线程，
任务来了交给空闲的线程跑，跑完线程不销毁，回去等下一个人。

## 二、正解：`ThreadPoolExecutor` 的七个参数

```java
ThreadPoolExecutor pool = new ThreadPoolExecutor(
        1,                                  // ① corePoolSize   核心线程数
        2,                                  // ② maximumPoolSize 最大线程数
        0L, TimeUnit.MILLISECONDS,          // ③ keepAliveTime + unit 空闲多久回收
        new ArrayBlockingQueue<>(2),        // ④ workQueue      任务队列
        r -> new Thread(r, "worker-" + n),  // ⑤ threadFactory  怎么造线程
        new ThreadPoolExecutor.AbortPolicy()// ⑥ handler        满了怎么办
);
```

（③ 其实是两个参数，所以常说是"七个"。）

### 2.1 执行顺序（最重要的一张图）

```
提交任务
   ↓
核心线程有空闲？ ──是──→ 交给核心线程
   ↓ 否
队列没满？ ──────是──→ 放进队列排队
   ↓ 否
线程数 < 最大？ ──是──→ 新建一个非核心线程
   ↓ 否
执行拒绝策略
```

真实输出验证了这个顺序：

```terminal
========== 2. 七个参数，和真实的执行顺序 ==========
  提交任务1 成功  (线程数=1, 队列=0)
  提交任务2 成功  (线程数=1, 队列=1)
  提交任务3 成功  (线程数=1, 队列=2)
  提交任务4 成功  (线程数=2, 队列=2)
  提交任务5 被拒绝  (线程数=2, 队列=2)
  提交任务6 被拒绝  (线程数=2, 队列=2)
```

核心 1、队列 2、最大 2。看 `队列` 那一列：

| 提交第几个 | 发生了什么 | 线程数 | 队列 |
|---|---|---|---|
| 1 | 核心线程还没满，直接跑 | 1 | 0 |
| 2 | 核心满了，**进队列** | 1 | 1 |
| 3 | 队列还有一个位 | 1 | 2 |
| 4 | 队列满了，**才**加线程 | 2 | 2 |
| 5 | 线程到上限、队列也满 → 拒绝 | 2 | 2 |
| 6 | 同上 | 2 | 2 |

**这里有个反直觉的点**：不是"核心满了就加线程"，而是
**"核心满了先排队，队列满了才加线程"**。

这个设计有它的道理：加线程比排队贵。但也带来一个坑——
**如果队列是无界的，那 `maximumPoolSize` 永远不会生效**，
因为队列永远不满，线程数永远停在 core。

### 2.2 四种拒绝策略

队列和线程都到上限之后怎么办：

| 策略 | 行为 |
|---|---|
| `AbortPolicy`（**默认**） | 抛 `RejectedExecutionException` |
| `CallerRunsPolicy` | **提交任务的线程自己跑** |
| `DiscardPolicy` | 静默丢掉，什么都不说 |
| `DiscardOldestPolicy` | 丢掉队列里最老的那个，再试一次 |

`CallerRunsPolicy` 特别值得说：

```terminal
========== 3. 队列满了之后的四种拒绝策略 ==========
  第三个任务由谁执行 → main（提交它的线程是 main）
  ← CallerRunsPolicy 让调用方自己跑，等于给上游一个背压信号
```

任务由 **`main` 线程**执行了。这不是 bug——它让调用方"自己承担代价"：
你的请求把池子打满了，那你就自己跑这个任务，于是你的处理速度自然慢下来。
这叫**背压**（backpressure），是一种温和的自我保护。

**生产上建议**：用 `AbortPolicy` 并**自己捕获异常**记录日志，
或者用 `CallerRunsPolicy` 做背压。**别用 `DiscardPolicy`**——
静默丢任务是最难排查的事故。

## 三、为什么阿里手册不让用 `Executors`

`Executors` 提供了几个快捷方法，看起来很方便：

```java
Executors.newFixedThreadPool(2);
Executors.newSingleThreadExecutor();
Executors.newCachedThreadPool();
Executors.newScheduledThreadPool(2);
```

《阿里巴巴 Java 开发手册》明确禁止用它们，理由是 **OOM 风险**。
我们把每个池的内部参数挖出来看：

```terminal
========== 4. 为什么阿里手册不让用 Executors ==========
  newFixedThreadPool(2)
    队列 → LinkedBlockingQueue，剩余容量 = 2147483647  ← 无界！
    最大线程数 = 2
  newCachedThreadPool()
    队列 → SynchronousQueue，剩余容量 = 0
    最大线程数 = 2147483647  ← 无界！
  newScheduledThreadPool(2)
    队列 → DelayedWorkQueue，剩余容量 = 2147483647  ← 无界！
    最大线程数 = 2147483647  ← 无界！
```

`2147483647` 就是 `Integer.MAX_VALUE`——"无界"的意思。

| 方法 | 问题 |
|---|---|
| `newFixedThreadPool` | 队列**无界**（`LinkedBlockingQueue`），任务堆积 → OOM |
| `newSingleThreadExecutor` | 同上，队列无界 |
| `newCachedThreadPool` | 线程数**无界**（最大 `Integer.MAX_VALUE`），来多少建多少 → OOM |
| `newScheduledThreadPool` | 队列无界，线程数也无界 |

**正确做法**：手动 `new ThreadPoolExecutor(...)`，把七个参数写清楚，
尤其**队列必须有界**。

### 3.1 顺带发现的一件事

写这一课时我想把每个池的内部参数打印出来，于是直接强转：

```java
ThreadPoolExecutor tpe = (ThreadPoolExecutor) Executors.newSingleThreadExecutor();
```

**直接抛异常了**：

```
java.lang.ClassCastException: class java.util.concurrent.Executors$AutoShutdownDelegatedExecutorService
    cannot be cast to class java.util.concurrent.ThreadPoolExecutor
```

原来 `newSingleThreadExecutor` 返回的不是 `ThreadPoolExecutor`，
而是一个**包装类**（`DelegatedExecutorService`）——它故意把
"改核心线程数"这类方法藏起来，让这个池真的只能有一个线程。

`newWorkStealingPool` 返回的是 `ForkJoinPool`，是另一套实现。

**教训**：`ExecutorService` 只是个接口，别假设它的实现一定是
`ThreadPoolExecutor`。这也是为什么 demo 里我先用 `instanceof` 判断。

## 四、`execute` vs `submit`

两个方法都能提交任务，差别在**异常和返回值怎么处理**：

| | `execute(Runnable)` | `submit(Callable/Runnable)` |
|---|---|---|
| 返回值 | 无 | `Future<T>` |
| 异常 | 冒到线程的未捕获处理器 | 包进 `Future` |
| 主线程能知道吗 | **不能** | 调 `get()` 才能 |

```terminal
========== 5. execute vs submit：一个吞异常，一个能拿到 ==========
  未捕获异常处理器收到 → execute-demo 抛了 IllegalStateException: execute 里抛的
  execute 提交的任务抛异常 → 主线程完全收不到（只有未捕获处理器知道）
  submit 提交的任务抛异常  → 不调 get() 的话同样看不到
  调 future.get() 之后    → 抛 ExecutionException，原因是 IllegalStateException: submit 里抛的
  submit 的返回值         → 42
```

这里有两个陷阱：

1. **`execute` 的任务抛异常，主线程完全不知道**。异常只会打印到控制台
   （除非你设了未捕获异常处理器）。任务"悄悄失败"就是这么来的
2. **`submit` 的异常包在 `Future` 里，不调 `get()` 就永远看不到**。
   这比第 1 条更隐蔽——因为你会以为 `submit` 更"安全"

**实用建议**：用 `submit` 就一定要 `get()`（或者用
`CompletableFuture` 的 `exceptionally` / `whenComplete` 处理）。

## 五、优雅停机

```terminal
========== 6. 优雅停机：shutdown vs shutdownNow ==========
  shutdown() 之后 isShutdown = true
  等它跑完 → 完成了 3 个，terminated = true
  shutdownNow() 返回了 4 个没来得及跑的任务
  ← 注意：它只是「尝试」中断，不响应中断的任务照样跑完
```

| | `shutdown()` | `shutdownNow()` |
|---|---|---|
| 接新任务 | 不接 | 不接 |
| 队列里的任务 | **跑完** | 返回给你，不跑 |
| 正在跑的任务 | 跑完 | **尝试** `interrupt()` |
| 返回值 | 无 | 没来得及跑的任务列表 |

**`shutdownNow()` 是"尝试"中断**——它给线程发中断信号，
但如果任务里没有检查中断标志（[线程通信](./16-线程通信.md)那课讲的），
它照样跑完。所以它并不能保证"立刻停"。

**标准停机姿势**：

```java
pool.shutdown();                                    // 1. 不再接新任务
if (!pool.awaitTermination(30, TimeUnit.SECONDS)) { // 2. 等一会儿
    pool.shutdownNow();                             // 3. 还不停就强制
}
```

## 六、线程工厂：给线程起名字

```java
ThreadFactory factory = r -> {
    Thread t = new Thread(r, "order-pool-" + counter.incrementAndGet());
    t.setDaemon(false);
    return t;
};
```

```terminal
========== 7. 线程工厂：给线程起名字 ==========
  任务跑在 → order-pool-1
  任务跑在 → order-pool-2
  任务跑在 → order-pool-3
  ← 线程名带业务含义，jstack 里一眼能认出是哪个池
```

默认线程名是 `pool-1-thread-1` 这种，出了事 `jstack` 里一片
`pool-7-thread-13`，你根本不知道是哪个业务的池。

**起名字是成本最低的可观测性投入**。业务名 + 序号，
排查问题时一眼就能定位。

顺带：线程工厂也是设置守护线程的地方（`t.setDaemon(true)`），
以及设置优先级、`UncaughtExceptionHandler` 的地方。

## 七、线程数怎么定

这是面试常问的，但**没有标准答案**，只有两个起点：

| 任务类型 | 经验公式 | 为什么 |
|---|---|---|
| **CPU 密集型** | 核数 + 1 | 线程都在算，多了只会增加切换开销 |
| **IO 密集型** | 核数 × 2，或更精确的 `核数 × (1 + 等待时间/计算时间)` | 线程大部分时间在等 IO，多开几个能让 CPU 不闲着 |

**更实用的做法**：先按公式设一个初值，然后**压测 + 监控**调整。
看这几个指标：队列积压、任务平均等待时间、CPU 利用率。

还有个比"调参"更重要的原则：**池要隔离**。

> 别让下单、查订单、发短信共用一个池。一个接口慢下来，
> 会把整个池占满，其他接口全部受影响——这叫**故障蔓延**。
> 按业务或按接口分组，各用各的池。

## 八、不推荐的用法

- **别用 `Executors` 的快捷方法**（生产环境）。队列或线程数无界，
  上面已经用真实数字证明
- **别用无界队列**。`LinkedBlockingQueue` 不传容量就是无界的，
  任务堆积到 OOM 才发现
- **别忽略 `submit` 返回的 `Future`**。异常被吞在里面，
  任务失败了你都不知道
- **别在任务里吞掉 `InterruptedException`**。停机时会卡住
- **别所有业务共用一个池**。池要按业务隔离，避免故障蔓延
- **别忘了停机**。程序退出前 `shutdown()` + `awaitTermination()`，
  否则正在跑的任务可能被硬切断

## 九、这一课的术语表

- **线程池**（thread pool）—— 复用一组线程执行任务的容器
- **`ThreadPoolExecutor`** —— JDK 的线程池实现，七个参数
- **核心线程数**（corePoolSize）—— 常驻线程数，即使空闲也不回收（默认）
- **最大线程数**（maximumPoolSize）—— 线程数上限
- **任务队列**（workQueue）—— 核心线程忙时任务排队的地方
- **拒绝策略**（RejectedExecutionHandler）—— 队列和线程都满时的兜底
- **`AbortPolicy` / `CallerRunsPolicy` / `DiscardPolicy` / `DiscardOldestPolicy`** —— 四种策略
- **背压**（backpressure）—— 让上游感知下游压力，`CallerRunsPolicy` 就是一种
- **线程工厂**（ThreadFactory）—— 自定义线程怎么创建（名字、守护、优先级）
- **`execute` / `submit`** —— 提交任务；前者无返回值、异常冒出去，后者包在 `Future` 里
- **`shutdown` / `shutdownNow`** —— 优雅停机 / 尝试中断并返回待跑任务
- **`awaitTermination`** —— 等池子真的停下来
- **故障蔓延**（cascading failure）—— 一个慢接口拖垮共享资源，进而拖垮全部
